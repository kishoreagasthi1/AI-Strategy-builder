# VYNE Platform — Handoff Notes (2026-09-09/10) — v5.34.22 → v5.34.30

Scope: the four live-voice symptoms from `FABLE_HANDOFF_live_voice.md` (S1 no reply,
S2 stuck mic button, S3 distortion, S4 fallback voice after refresh). Verified
behaviour in 5.34.21 (opening, pause/resume keepalive) was NOT touched.

## Diagnosis — what the code proves, and what it does not

**The "two systems fighting" hypothesis is real, but it is NOT what happens
before anyone clicks.** Traced every path that starts the legacy recogniser
(`VyneRecognition` in vyne-client.js — its own `getUserMedia` + `MediaRecorder`):
`toggleMic()` (the mic button), `onSpeakEnd()` (auto-mic after TTS), and the
resume branch of `setInterviewPaused()` when `LIVE` is null. On a clean live
interview none of these fire until a person clicks the mic. So the second
capture chain cannot explain the FIRST no-reply — it explains everything after
the interviewee gives up waiting and clicks.

| Symptom | Cause (proven from code unless marked) | Fixed by |
|---|---|---|
| **S2** stuck red "RECORDING" | The voice bar showed the standard controls on the live path — the placeholder literally said "Click 🎤 to start". `toggleMic()` then started `VyneRecognition`: a SECOND mic stream + MediaRecorder + the red banner, while the live session's own capture kept streaming. `VyneRecognition.start()` is async and silently no-ops if `_rec` exists, so a quick second click leaves it recording with nothing to stop it. | mic button is a no-op indicator while live owns the mic; recogniser is never built on the live path |
| **S4** "VYNE_Agent" after hard refresh | A refresh closes the socket but never ran `stop()`, so the server-side hold was never released. Holds count for 10 min against a cap of 3 (`routes/voice.ts`). The 3rd refresh in 10 min → `429 too_many_live_sessions` → the page's designed fallback: text model + TTS ("VYNE Agent" bubbles, default persona). Same mechanism as HANDOFF_2026-09-08 item 1. | `pagehide` → `LIVE.stop('page_unload')` → keepalive `/close` beacon (verified in headless Chromium: `/close` fires on reload) |
| **S3** distortion | Two mechanisms, both real: (a) after any moment where `liveActive()` was false (renewal in flight, grant lapsed), `sendToAgent` fell to the text path → `speak()` (TTS) → `onSpeakEnd` → auto-starts the recogniser. Now two voices AND two mics. (b) *Suspected, now instrumented*: the model interrupting itself on its own echo (`interrupted` with a quiet uplink) → `flush()` every few hundred ms = choppy audio. | (a) `speak()` is suppressed while live owns output; routing is by ownership not liveness; (b) `INTERRUPTED — barge-in {likelySelfEcho}` trace line |
| **S1** no reply after speaking | **Not provable from code — and no prior trace ever showed an `inputTranscription` frame for the interviewee.** "mic: N frames" only proved frames FLOWED. The candidates, in order: (1) the model never hears — uplink carries silence/garbage (browser-specific capture chain; Safari does not resample a mic stream into a 16 kHz context); (2) the model hears but VAD never closes the turn (continuous noise/echo keeps it "open"); (3) the model hears and answers, but only after a multi-second *thinking* phase — the UI showed "Listening..." throughout, which reads as dead and sends the person to the mic button (→ S2). | Instrumentation that separates (1)/(2)/(3) in one trace, the visible mic meter and per-turn status for (3), and an opt-in `thinkingBudget` knob for (3) |

The Gemini Live contract was re-checked against current docs: `realtimeInput.audio`
with `audio/pcm;rate=16000` and automatic VAD (default on) is exactly what
`buildAudioFrame` sends — no `activityStart/End` needed. Two facts worth knowing:
gemini-2.5 native audio has **dynamic thinking on by default** (the 3–15 s of text
frames before every reply, not just the opening; `thinkingBudget: 0` disables it),
and the WebSocket **connection** lifetime is ~10 min regardless of the 15-min grant
(handled by the existing renewal; now a typed message during the gap is held, not
sent to the text model).

## What changed (5.34.22)

**One owner.** `interview_agent.html`
- `liveOwnsConversation()` = `LIVE && !LIVE.stopped` — sticky through a renewal, ends
  only when live is over for good. `sendToAgent` routes on this, not on `liveActive()`.
- `toggleMic()`, `speak()`, `onSpeakEnd()` are no-ops while live owns the interview.
- The recogniser is built only on the standard path (on the tap, after live was not
  taken; or lazily in `toggleMic`). Never on a live interview.
- Live voice bar: 🎤 becomes an indicator with a **level meter** (green = the app hears
  you); placeholder says "just speak"; status shows "*Jack Smith* is thinking… /
  is speaking — you can interrupt / Listening...".
- `pagehide` releases the live grant.

**Bridge.** `vyne-live-interview.js`: `say()` holds text while no socket exists and
sends it into the renewed session; a failed renewal or a non-paused terminal end
sets `stopped=true` (live path over → standard path may take over cleanly).

**Instrumentation.** `vyne-live.js` (all in `vyneLiveLogDump()`):
- `mic: first frame sent {rms, peak, track{readyState,muted,label,rate,ec,ns,agc}}`
- `mic: SPEECH on uplink (utterance starts) {rms, msSinceTurnComplete, agentPlaying}` /
  `mic: utterance ends (~Ns of speech)`
- `!!! mic uplink SILENT for 8s while unmuted` → candidate (1) above. Badge shows it.
- `USER TURN #n — model transcribed the interviewee; awaiting its reply`
- `model ACTIVITY on user turn #n (Xms after transcript began)` / `reply FIRST AUDIO`
- `!!! NO MODEL ACTIVITY 12s after the interviewee was transcribed` → candidate (2).
  Badge shows it.
- `INTERRUPTED — barge-in {micRms, micInUtterance, likelySelfEcho}`
- `playback run starts {ctxRate, resampledByBrowser, leadMs}` / `run ends {chunks,
  audioSec, wallSec, stillQueuedSec}` / `!!! PLAYBACK OVERLAP` → S3 inside the queue
- `recognition.start()/stop() {liveOwns, via}`, `sendToAgent() {liveOwns, via}`,
  `callClaude() — TEXT path taking a turn {via}`, `speak() SUPPRESSED`
- DevTools: `await vyneLiveMicCheck(3)` → `{peakRms, speechLevel, track}` — say
  something after calling it.

**Opt-in.** `GEMINI_LIVE_THINKING_BUDGET=0` (Cloud Run env; forwarded by deploy.sh)
pins `generationConfig.thinkingConfig.thinkingBudget` into the token. Unset = wire
identical to 5.34.21. If Google rejects the field, the mint retries WITHOUT it and
stays pinned (the persona pin is never traded for the knob); the grant echoes
`thinkingBudget` so `grant minted` in the trace shows what applied. **Not verified
against the live API** — try it on staging first and read the `grant minted` line.

## By-ear verification (the only acceptable sign-off)

Fresh tab, hard reload (⌘⇧R), confirm the badge/version reads 5.34.22, DevTools open.

1. Tap to begin. Expect: `● Live voice — Sadaltager`; 🎤 shows a small bar under it;
   placeholder "Live voice — just speak…". Jack Smith speaks his opening (≤ ~7 s).
2. While he speaks: the bar should stay grey/low (your room). Interrupt him mid-
   sentence: he must stop within ~0.5 s. Trace: `INTERRUPTED — barge-in
   {micInUtterance:true, likelySelfEcho:false}`.
3. Answer a question (2–3 sentences), then stop talking. Watch three things in order:
   the bar goes green while you talk; status changes to "Jack Smith is thinking…"
   within ~2 s of you stopping; then "is speaking" and you hear the reply.
   Trace: `mic: SPEECH on uplink` → `USER TURN #1` → `model ACTIVITY on user turn #1`
   → `reply FIRST AUDIO … {msAfterUserTurn}` → `model turn ENDS`.
4. Click the 🎤 button. Expect a toast ("Live voice is on — just speak") and NOTHING
   else: no red RECORDING banner, no change of state. Trace: `CLICK: mic button while
   LIVE owns the mic — ignored`. There must be NO `recognition.start()` line anywhere.
5. Pause 15 s, Resume. Answer again → reply. Trace: `paused — sending silent
   keepalive` … `resumed — capture chain state {track.muted:false}` … `USER TURN #2`.
6. Type a sentence in "Type instead" and send. Reply must come in Jack's voice.
   Trace: `sendToAgent() {liveOwns:true}` and NO `callClaude()` line.
7. Hard-refresh three times in a row, tapping to resume each time. Every time must
   come back as `● Live voice`, never `○ Standard voice — too many open sessions`.
   Network tab: `POST /api/voice/live-session/close` on each refresh.
8. Let a session run past 10 minutes without pausing. Expect the badge to flash
   `reconnecting (1)` and Jack to continue; no VYNE Agent voice at any point.

If step 3 fails, the trace now says which of the three S1 candidates it is:
- `!!! mic uplink SILENT` → capture chain. Check `track.muted`, `label` (right device?),
  browser (Safari?), and run `await vyneLiveMicCheck(3)` while talking.
- `USER TURN #1` but then `!!! NO MODEL ACTIVITY` → server-side turn never closed.
  Look at what came BEFORE: `mic: SPEECH on uplink` lines that never get an
  `utterance ends` (constant noise/echo holding VAD open), or `INTERRUPTED
  {likelySelfEcho:true}` bursts. Headphones for one run isolates echo.
- `USER TURN #1` → `model ACTIVITY … kind:"thinking-text"` → `reply FIRST AUDIO` at
  8–15 s → it was latency all along. Set `GEMINI_LIVE_THINKING_BUDGET=0` on staging
  and re-run steps 1–3.

## 5.34.23 — what the first production trace of 5.34.22 showed, and what changed

Trace (Kishore, prod, 5.34.22), decoded against wall-clock since page load:

| t | line | meaning |
|---|---|---|
| 30.4 s | `model turn ENDS` | opening finished generating (playback ran on ~12 s) |
| ~43–50 s | 17.3 s "utterance" ends | opening echo + the interviewee's first answer (~7 s) |
| 50–101 s | **nothing from the server** | no `userTranscript`, no thinking text, no audio for 50 s |
| 59, 77, 84, 87 s | 0–0.9 s blips, rms 0.02 | "hello?" — quiet but speech-level |
| 92.7–97 s | 3.2 s utterance, peak 0.996 | a loud repeat |
| 101.4 s | `INTERRUPTED` + `turnHadAudio:false` | **the server WAS generating a turn that never produced a frame**, and the 101 s speech cut it |
| 111.1 s | audio run starts | reply, ~5 s after the 101–106 s utterance's VAD end — normal latency |
| 120.6 s | `INTERRUPTED` with `micRms:0.0002` | the server "heard speech" while our uplink was flat — it reacted to audio we sent **earlier** |
| 120.7 s | `mic uplink SILENT` | **false alarm** (noise-suppression floor); fixed below |

Reading: the uplink carried speech (levels 0.02–0.3, peaks to clipping), the capture
chain is fine, and the server did react — **late**. A turn open for 50+ s with no
output, then a reply, then an interruption from speech that ended 8 s earlier, is
the signature of a **delayed uplink**: the server hears every utterance seconds to
tens of seconds after it was said. Two places that delay can live: (a) in the
browser/network — `ws.bufferedAmount` climbing because the socket is not draining
(VPN, proxy, upstream bandwidth, server backpressure); (b) inside Google's pipeline
after it has our bytes. 5.34.22 could not tell them apart. 5.34.23 can.

### Changes
- **`wsBuffered` / `backlogSec`** on every mic rollup, utterance start/end and
  INTERRUPTED line; `!!! UPLINK BACKLOG — N s of audio is queued in the browser` once
  it passes 1 s; past 3 s frames are **shed** (`uplink SHEDDING frames`) so latency
  stays bounded instead of growing; `uplink backlog drained {droppedFrames}`.
- **No uplink before `setupComplete`.** Frames used to leave in the ~130 ms between
  our setup message and the server's ack. Google's client never does that.
  `setupComplete … {micFramesHeldBeforeSetup:N}` shows how many were held.
- **`!!! SERVER IGNORED ~Ns of speech-level uplink`** — a client-side utterance ≥1 s
  with no server reaction of any kind within 8 s, with a verdict: `uplink is QUIET
  (meanRms < 0.02)` or `level is fine — server-side turn detection`. Badge: "your
  voice is not reaching the interviewer". This is the line 5.34.22 could not write
  because it waited for a transcription that never came.
- **Silence detector** fixed: 15 s window, rms 0.0003 **or** peak 0.005 counts as
  non-silent, and an utterance resets it. Chrome's NS floor (0.0002–0.0008) no
  longer trips it.
- **Experiment flags** (persist across hard reload; default all OFF = wire identical):
  `vyneLiveFlags({micGain:3})` amplify uplink; `vyneLiveFlags({streamEnd:true})`
  send `audioStreamEnd` after each utterance (documented flush); `vyneLiveFlags
  ({manualVad:true})` disable server VAD and bracket utterances with
  `activityStart/activityEnd` from the client-side detector; `vyneLiveFlags(null)`
  clears. Active flags are logged as `EXPERIMENT FLAGS ACTIVE`.
- **Hear what the model hears:** `vyneLivePlayUplink(10)` plays the last 10 s of the
  exact PCM sent to Google; `vyneLiveDownloadUplink(30)` saves it as WAV.
- `INTERRUPTED` line now carries `msSinceLastUtteranceEnd`, `playbackPending`,
  `wsBuffered`, `uplinkQuietNow` (no more "likelySelfEcho" — it asserted a cause).

### Next run — what to look at, in order
1. Trace after the first answer: `wsBuffered` on the mic rollups. **Climbing into the
   tens of KB and `backlogSec ≥ 1` → the browser/network is the lag** (try another
   network / no VPN; the shedding keeps it usable meanwhile). **Flat near 0 → the lag
   is inside Google after it has the audio** → go to 2.
2. `SERVER IGNORED` lines: `uplink is QUIET` → `vyneLiveFlags({micGain:3})`, reload,
   repeat. `level is fine` → `vyneLiveFlags({streamEnd:true})`, reload, repeat; if
   still late, `vyneLiveFlags({manualVad:true})`.
3. If replies come but 10–20 s late with `thinking-text` in `model ACTIVITY … kind`,
   set `GEMINI_LIVE_THINKING_BUDGET=0` on the API service and redeploy.
4. `vyneLivePlayUplink(10)` right after an answer: you should hear yourself, clear,
   normal pitch. If not, send `vyneLiveDownloadUplink(30)`'s WAV with the trace.

## 5.34.24 — the 5.34.23 trace settles WHERE the fault is

Second production trace (Kishore, 5.34.23):
- `wsBuffered: 0, backlogSec: 0` on every line → **the uplink leaves the browser
  in real time.** Not the network, not the browser.
- 23.8 s answer, `meanRms 0.0586, peak 0.903` → **level is fine**, format verified
  (40 frames per 5.12 s = a true 16 kHz context).
- **Nothing** from the server for it, nor for a 2.7 s answer, nor three short ones.
  `!!! SERVER IGNORED ~23.8s … verdict: level is fine — server-side turn detection`.
- The 22 s opening produced **zero `outputTranscription` frames** although the
  client's setup asks for both transcriptions → the client's setup frame is not
  (fully) honoured on the constrained endpoint. This is the same class of silent
  behaviour as the v5.32.53 speechConfig incident: the endpoint ignores what it
  does not expect rather than rejecting it.
- Pause keepalive, resume, opening: all still correct.

Conclusion: **Google's side of the socket is not treating our realtime audio as a
user turn**, and the remaining causes are all about the server's turn/setup state,
not about capture. Each has a flag now.

### Changes
- **Token carries the extras.** The mint now pins `inputAudioTranscription`,
  `outputAudioTranscription` and (when the browser asks via `manualVad`) 
  `realtimeInputConfig.automaticActivityDetection.disabled` into the token, with
  the same shed-before-unpin ladder as the thinking budget. `grant minted` shows
  `pinnedExtras:{transcription, manualVad}`. **If transcripts start appearing
  only now, the client setup was being ignored — that alone is worth knowing.**
- New flags (persisted, default off): `legacyChunks` (audio as
  `realtimeInput.mediaChunks[]`, the older field — an ignored `audio` field would
  look exactly like this), `openingViaRealtime` (text as `realtimeInput.text`, so
  the session never mixes clientContent turns with realtime audio),
  `holdMicUntilFirstTurn` (no mic audio while the opening is generating/speaking).
  `manualVad` now also travels to the server.

### Run order (one flag per run, hard reload between, `copy(vyneLiveLogDump())` each)
0. **No flags.** Read `grant minted … pinnedExtras`. Speak one answer. If
   `agentTranscript`/`userTranscript` lines now appear and the reply comes → the
   client setup was the whole problem; done.
1. `vyneLiveFlags({holdMicUntilFirstTurn:true})` — tests "audio during the
   clientContent turn poisons the turn state".
2. `vyneLiveFlags({holdMicUntilFirstTurn:false, openingViaRealtime:true})` —
   tests "mixing the two input paths".
3. `vyneLiveFlags({openingViaRealtime:false, legacyChunks:true})` — tests "the
   `audio` field is ignored on this endpoint".
4. `vyneLiveFlags({legacyChunks:false, streamEnd:true})`, then
   `vyneLiveFlags({streamEnd:false, manualVad:true})` — server VAD end-of-turn.
5. `vyneLiveFlags(null)` to clear. Whichever run produces `USER TURN #1` → `model
   ACTIVITY` → `reply FIRST AUDIO` within ~5 s of you stopping is the fix; it
   then becomes the default in the next build and the other flags are deleted.

realtime audio as a turn and emitting transcriptions is the half that has never
worked — and v1alpha, second in the sweep, has never been tried on a real session.
That fits every trace better than any other single hypothesis.

- New flag: `vyneLiveFlags({v1alpha:true})` → sweep order starts with
  `v1alpha/BidiGenerateContentConstrained?access_token`. Trace shows `ws variant

## 5.34.27 — FOUND IT IN THE TRACE: Google rejects the audio turn (close 1007)

Fifth trace (5.34.25 frontend, still the OLD API — `pinnedExtras: undefined`, v1beta):

```
[VL + 24394ms] frame MODEL-TEXT  "**Analyzing the Utterance** I've processed the Hi… 'Have to achieve anything'…"
[VL + 26322ms] frame MODEL-TEXT  "**Formulating a Response** …"
[VL + 28402ms] ws CLOSE — code 1007 — The audio content type (CONTENT_TYPE_AUDIO) is not
               supported for this model configuration.
```
…and again 7 s later on the renewed session. Then a third session DID answer with
audio, then ignored a 24 s answer outright.

So the model **hears** the interviewee — its thinking quotes their words — and when it
goes to generate the reply, Google closes the socket: the model configuration does
not support audio content. Sometimes the reply survives, sometimes the socket dies,
sometimes nothing comes back at all; all three are the same server-side fault seen
from the client. The LiveKit community hit this exact close on 2026-09-06 on
`gemini-2.5-flash-native-audio-preview-12-2025`
(https://community.livekit.io/t/…/1737) — four days ago, same model family. Our
model is the `-latest` alias, which tracks whichever preview Google points it at.

Consequence that was invisible until now: each 1007 triggered an instant renewal =
a fresh grant. Two in 8 s. That is a second road to `too_many_live_sessions` and the
text+TTS fallback ("VYNE_Agent"), and every renewal starts a session with NO memory
of the conversation so far.

### Changes (client)
- `!!! GOOGLE REJECTED AN AUDIO TURN — 1007 CONTENT_TYPE_AUDIO` trace line with
  model/variant/pinned/thinkingBudget/pinnedExtras; badge "Google rejected your last
  answer (1007 audio) — reconnecting".
- Renewal after a 1007 waits 1.5 s; three consecutive 1007s end the live path with
  reason `audio_rejected` and a badge that says so, instead of burning the grant cap.

### What to change on the SERVER (this is where the fix is)
Deploy the API (it is still on a pre-5.34.24 build — `pinnedExtras: undefined`) and
set, in this order, one at a time:
1. **`GEMINI_LIVE_MODEL=models/gemini-2.5-flash-native-audio-preview-09-2025`** —
   pin off the `-latest` alias. If `-latest` now resolves to the 12-2025 preview that
   LiveKit users see failing, this alone may fix it. (This is not the "wrong model"
   mistake from 5.34.18 — both are on `LIVE_CAPABLE_MODELS`.)
2. **`GEMINI_LIVE_THINKING_BUDGET=0`** — the 1007 lands right after the thinking
   frames every time; thinking + audio input on a pinned config is the obvious
   interaction to remove.
3. v1alpha (default since 5.34.26) — the token endpoint is v1alpha; a v1beta session
   holding a v1alpha token is the other candidate for "this model configuration".

Sign-off is unchanged: opening → answer → reply within ~5 s, no `1007`, no `SERVER
IGNORED`, `agentTranscript` lines present, Pause/Resume, and a typed message answered
in Jack's voice.

## 5.34.28 — first v1alpha trace: it ANSWERS. Late. API still not deployed.

Seventh trace (5.34.26/27 frontend, v1alpha default; `!!! API BUILD MISMATCH` — the
API service is STILL on the pre-5.34.24 build):

| | v1beta (all earlier traces) | v1alpha (this trace) |
|---|---|---|
| opening: trigger → first audio | 7–10 s (thinking 5–7 s) | **4.3 s** (thinking 2.2 s) |
| reply to a spoken answer | never, or `1007 CONTENT_TYPE_AUDIO` | **yes** — twice, with audio |
| latency, answer end → reply | — | 13.5 s and ~28 s |
| `1007` closes | 2 in one run | **0** |
| transcription frames | none | none (extras not pinned — API not deployed) |

So the endpoint mattered: v1alpha talks back on this token; v1beta refuses or dies.
What is left is latency and one behaviour of the interviewee: after the first answer
the trace shows six 0.3–0.5 s utterances ("hello?") over 25 s, and `INTERRUPTED`
right after the first of them — each one cancels the reply the model was preparing
and starts it over. **After answering, stay silent until the reply starts.**

The 13–28 s is not the model thinking (thought summaries arrive ~0.5 s before the
audio); it is the server deciding the interviewee's turn has ended. That has
documented controls, now pinned into the token from env (API deploy required):

## 5.34.33 — long sessions, and a harness that does not need a human

The 3.1-flash-live run was good for ten minutes and then stopped, with a
probable sign-out. Three defects, all ours, all provable from code:

1. **A 401 or an idle expiry replaced the page mid-interview.** Both ends of
   the session policy in `vyne-client.js` finished with
   `location.href = "index.html?expired=1"`, whatever else was happening. The
   realtime socket talks to Google with an ephemeral token and needs nothing
   from our API, so the interview was still working when the page was taken
   away — and the in-memory trace went with it, which is why the failure could
   not be read afterwards. Now: the sign-out is deferred while a live session
   owns the page (`window.__vyneLiveActive`), the local token is dropped
   immediately either way, and the redirect fires when live goes idle or after
   a 20-minute cap.
2. **Idle was measured only from click/keydown/mousemove/touchstart.** A
   hands-free interview produces none of them, so the 30-minute sweep signed
   the interviewee out mid-sentence while they were audibly present.
   `vyne-live.js` now calls the exposed `vyneTouchSession()` on each utterance
   and each model turn: talking is activity.
3. **The trace died with the page.** It is now mirrored into localStorage
   (tail-bounded, flushed on pagehide) and the previous page instance's copy is
   readable with `copy(vyneLiveLogDumpPrev())`.

### 90–120 minute deep dives
- **`MAX_RENEWALS = 8` was a duration limit in disguise.** One handover per
  ~10 minutes means twelve for two hours; renewal nine ended the live path at
  about eighty minutes. Renewals are now bounded by DURATION
  (`VYNE_MAX_INTERVIEW_MS`, default 3 h) with a high count guard (40).
- **The concurrency guard refused the continuation of the session it had just
  admitted.** A handover mints a fresh grant; with any stranded holds in the
  rolling window (an earlier interview whose `/close` never landed — see
  defect 1) the renewal got a 429 and the interview stopped dead. The client
  now sends `renewalOf: <previous sessionId>` and `admitLiveSession` exempts a
  VERIFIED continuation from the concurrency check only — spend caps and the
  reservation are untouched, so the exemption cannot buy budget.
- **A stale `goAway` survived into the replacement connection** and handed it
  over again ~1 s later: two handovers where one was needed, an extra grant,
  and a second gap in the conversation. Found by the soak, not by a person.
  `_openSession` now clears `_goAwayPending` and the poll.
- **An interview that ends early is not lost.** `onEnded` saves
  synchronously (the turn-by-turn autosave is debounced 1.2 s, so the last
  exchange could be the one that never landed), says the answers are saved and
  names the resume code. `buildLiveContext()` feeds the recent transcript back
  in on resume via `priorTranscriptBlock()`, so the interviewer picks up
  instead of re-asking covered ground.

### Testing without a human (this was the ask)
- `backend/test/liveLongSessionSoak.test.ts` — drives the SHIPPED frontend
  modules through a full two-hour interview in ~6 seconds: 12 goAway
  handovers, 36 exchanges, the grants and closes they generate, against a fake
  Google that only issues resumption handles at turn boundaries. Asserts the
  interview never ends, every renewal carries the handle, holds do not
  accumulate, and the cap never refuses a continuation. Includes the negative
  control (without `renewalOf` the same handover IS refused) and a regression
  pinning the old 8-renewal death at ~80 minutes.
- `backend/test/liveSessionExpiryDeferral.test.ts` — runs the shipped
  `vyne-client.js` in a vm and asserts on NAVIGATION: a 401 mid-interview does
  not redirect, an idle expiry mid-interview does not redirect, both fire the
  moment live ends, an explicit sign-out is still immediate.
- `deploy/soak-live.mjs` — the unattended REAL-Google soak, which is the only
  thing that can answer "does Google still answer promptly at minute ninety".
  `GEMINI_API_KEY=… node deploy/soak-live.mjs --minutes 120 [--wav answers.wav]`

## 5.34.39 — FOUND IT: the project is being rate-limited by Google

Six unattended 10-minute runs, same afternoon, same script, same key.

| # | run | config | turns | answered | median | connection ends |
|---|---|---|---|---|---|---|
| 1 | base | default thinking, compress 25600 | 35 | 34 | **1,196 ms** | goAway, 1011 internal |
| 2 | think | thinkingLevel LOW | 28 | 28 | 2,719 ms | goAway, deadline |
| 3 | nocompress | compression OFF | — | — | (no verdict) | — |
| 4 | budget | thinkingBudget 0 | NEVER RAN | — | — | — |
| 5 | base2 | **identical to run 1** | 12 | 6 | **31,844 ms** | 1011 internal ×3, **1011 Resource has been exhausted (e.g. check quota)**, deadline |
| 6 | gen25 | 2.5 native audio | 8 | 3 | 4,961 ms | **1011 The service is currently unavailable** |

**Run 1 and run 5 are the same configuration.** 1,196 ms and 34/35 answered,
versus 31,844 ms and 6/12 answered. The only difference between them is how
much of the project's Live API allowance had already been spent, and run 5 says
so in Google's own words: *Resource has been exhausted (e.g. check quota)*.
Run 6 says the same thing differently: *The service is currently unavailable*.

So the answer to "why does the interview start well and then degrade" is not
the model, not the session length, not thinking, not context compression, not
the VAD settings, and not this code. It is a project-level rate limit, and
every one of those settings was tuned against its shadow. Three more things
that follow from the same evidence:

- **3.1 Live does not degrade with session length.** Run 1: flat ~1.2 s across
  34 turns and 10 minutes, one goAway handover ridden cleanly with resumption.
  The product is capable of a good long interview on a rested quota.
- **`thinkingLevel` is accepted by 3.1; `thinkingBudget` is still unverified**
  because run 4 never executed. That remains the one open configuration
  question, and it matters: the product pins `thinkingBudget`, so if 3.1
  rejects it the env var has been inert all along.
- **2.5 native audio exposes thought time** (`thought 2382ms of it`), which 3.1
  does not, and was also throttled — so this is not a 3.1-preview problem.

### Changes (product)
- `vyne-live.js` recognises a RESOURCE_EXHAUSTED close and names it:
  `!!! GOOGLE IS RATE-LIMITING THIS PROJECT`. It used to arrive as an ordinary
  close and present to the interviewee as silence, which is precisely why it
  survived nine releases of investigation.
- `vyne-live-interview.js` backs off instead of re-minting instantly — 15 s,
  30 s, 60 s, 120 s, then ends with the named reason `quota_exhausted`. The old
  behaviour reconnected within milliseconds, spending the allowance that had
  just run out; run 5's five connections in ten minutes are what that looks
  like. An ordinary 1011 still renews immediately.
- `interview_agent.html` tells the interviewee the truth — "Google is
  rate-limiting this project — your answers are saved; resume in a few
  minutes" — rather than leaving a silence they read as a broken product.
- Six tests in `liveTurnOwnership.test.ts` cover naming, the wait, the
  escalation, the named give-up, and that a plain 1011 is NOT treated as a
  rate limit.

### Changes (soak)
- "the model transcribed NOTHING — this is the fixture" is now only printed
  when nothing was transcribed in the WHOLE run. In run 6 the same clips were
  transcribed cleanly for three turns and then not at all, and the script
  blamed my harness for Google refusing to work.
- The verdict flags any quota/availability close and prints
  `INVALID FOR COMPARISON` rather than a latency table, because a throttled run
  measures the allowance, not the setting under test.

### What to do about the quota
Live API limits are per project and per usage tier, and audio burns tokens
fast (~25 tokens/second in each direction). Check the real numbers for this
project rather than guessing:

    https://console.cloud.google.com/apis/api/generativelanguage.googleapis.com/quotas?project=vyne-platform-prod

Look at the concurrent-session and tokens-per-minute limits for the Live
models, and request an increase if a 90–120 minute deep dive is the target: two
hours of audio at ~25 tokens/second each way is on the order of 360k tokens of
throughput for ONE interview, before any testing around it. Until then, space
soak runs and real interviews apart — back-to-back sessions are what produced
run 5.

### The one run still owed

Run it from a rested quota. `setup accepted:` vs `REJECTED thinkingConfig`
answers whether the product's own thinking pin does anything on 3.1.

## 5.34.40 — the reply that arrives as TEXT and never as VOICE

I ran the soak myself this time, on the user's machine through the desktop
bridge (the cloud container and the device workspace are both blocked from
`generativelanguage.googleapis.com` by the org egress policy — an allowlist

**But turn 5 is the find:**

    conn 1 turn 5: reply NONE
      | heard "Skills are the part I worry about most. We can hire data eng"
      | said  "How is the organization addressing that knowledge gap on the business side?"

A healthy socket. The model UNDERSTOOD the answer and COMPOSED its next

### Changes
- `vyne-live.js` accumulates the turn's output transcript and, after

  there is nothing left to wait for. Audio arriving cancels the timer, and if
  the app had already started speaking, `onAudioArrivedLate` tells it to stop.
- `interview_agent.html` speaks that text with TTS. This is the ONE exception
  to "TTS never plays over a live session" (S3 in the original handoff), and it
  is bounded: only the turn's own text, only when no audio came, cancelled the
  instant Google's voice arrives, and never while paused. The badge says "no
  voice from Google on that reply — reading it aloud". This is also why the TTS
  model fix in 5.34.37 mattered: the fallback would have 404'd.
- Six tests: the mute window, no fallback when audio is timely, cancel on late
  audio, immediate fire on turnComplete, silence while muted.

## 5.34.41 — the 5.34.40 fallback made the voice choke; it is now opt-in

First real interview on 5.34.40: "the voice is choking every other second —
stop-go-stop-go". That is a regression I introduced, and the mechanism is in
this file's own history.

`vyne-live.js`'s INTERRUPTED handler resets `_turnAudio = false` on a barge-in
(correctly — the turn's audio was flushed). 5.34.40 read that flag as "no voice
has come for this turn", so the six-second mute-reply timer re-armed MID-TURN,
the TTS fallback started speaking, the microphone picked up that speech, Google
read it as another barge-in and flushed its playback again. Stop, go, stop, go.
The comment directly above the reset already names this shape as the
self-cancelling agent that reads as "distortion" (S3) — the exact failure this
project opened with.

The judgement: a mitigation for an occasional text-only reply must never
degrade the voice path it exists to protect. So the halves are separated —
- **Detection stays ON, always.** `!!! REPLY WITH NO VOICE` and `!!! MUTE TURN`
  still appear in the trace, because naming that failure cost two soak runs to
  discover and costs nothing to keep.
- **Speaking is OFF by default**, behind `vyneLiveFlags({ speakMuteReplies: true })`.
- **And when enabled it is guarded**: never while playback is pending, never
  after this turn was interrupted (`_turnWasInterrupted`, cleared at
  turnComplete), never while muted.

Five tests pin it, including the regression itself: speak + interrupt +
transcript must produce no fallback voice.

### Also: the interviewer has a name
Every chat bubble said "VYNE Agent" from a hardcoded string, while the assigned
identity (`S.interviewerName`, e.g. "Jack Smith") is what the persona
introduces itself as and what the voice says aloud in its first sentence — two
different people in one conversation. `agentLabel()` and `agentInitials()` now
resolve the live session's interviewer name, falling back to "VYNE Agent" only
when no identity was assigned.

## 5.34.42 — the 10-minute handover was a coin flip, and a lost toss killed the interview

The interview on 5.34.41 ran well for ten minutes and then went permanently
silent. The trace says exactly why, with no inference needed:

```
587703  setupComplete — session is live
587705  sendText -> WIRE  "Our connection was briefly renewed…"
598390  userTranscript "Are you there?"
610394  !!! NO MODEL ACTIVITY 12s after the interviewee was transcribed
```

**Two milliseconds after setupComplete.** That is precisely the warmup instant
`open()` exists for — this file has said since 5.34.16 that "setupComplete does
not mean the model can generate yet; a turn sent in that instant is sometimes
silently dropped", and 5.34.17/.19 built resilient retry machinery around it.
All of it protected the OPENING only. The renewal nudge, sent on every ~10-minute
goAway handover, went out as a bare `say()` — no liveness check, no retry, no
alarm. So every handover was a coin flip, and a lost one left the interviewee
talking to a socket that would never answer, for the rest of the interview.

Two changes, both in `frontend/vyne-live-interview.js`:

1. **The nudge goes through `open()`.** Same code, same guarantee as the
   opening: reset the new session's frame flags, send, and resend ONCE if
   nothing at all comes back (`VYNE_OPEN_RETRY_MS`, 12 s). A model that is
   merely *thinking* has set `_gotAnyModelFrame` and is left alone — the
   5.34.19 lesson about four resends restarting the introduction applies here
   unchanged.

2. **`_watchRenewedSilence()` — a resumed session that is itself wedged.**
   `open()`'s retry rescues a dropped turn; it cannot rescue a connection that
   is alive and mute, which is what the trace above actually shows (empty
   `speechState` frames for the rest of the interview). If no model frame of any
   kind arrives within `VYNE_RENEW_SILENCE_MS` (20 s) of a handover, the
   resumption handle is **dropped** and a fresh connection is minted. A handle
   that yields a mute session is worse than no handle, because the alternative
   is not amnesia: `buildLiveContext()` still carries the recent transcript
   across, so the interviewer picks the thread back up without Google's own
   memory of it. One recovery attempt per renewal; if the fresh connection is
   mute too, the interview ends with the named reason `renew_silent` — which
   goes through the 5.34.33 synchronous save, so the answers survive and the
   session code resumes.

`isRenewable()` gained `renew_silent_retry`. `_openSession()` clears the
watchdog alongside the stale goAway. The page shows "Reconnecting your
interviewer" on `onRenewSilent` and a resume message on `renew_silent`, rather
than leaving the interviewee listening to nothing.

Six tests in `liveTurnOwnership.test.ts`, all against the shipped frontend in a
vm: the nudge lands on the NEW socket and is resent into total silence; it is
NOT resent when the model is thinking; a mute resumed session drops the handle
and reconnects (asserted on the grant body — `resumeHandle` present on the
renewal, absent on the recovery); a second silence ends with `renew_silent`; and
a renewed session that DOES speak is never torn down.

### Not a code change: what "Clarify this answer" is
It appears under the **interviewee's own** answers
(`!isAI && !extra.docInfo && !extra.isClarification`), never under Jack's
questions. It opens a box to amend or expand what they just said — the wording
is being read as "the agent could not understand you", which is why it showed up
in the same breath as the silence. Worth renaming to something like
"Add to this answer".

### deploy/voice-record.mjs — the test that was missing

Three ways to test the live path now exist, and each one answers a question the
other two cannot:

| | runs our code | real Google | audible |
|---|---|---|---|
| `backend/test/liveTurnOwnership.test.ts` | yes | no | no |
| `deploy/soak-live.mjs` | **no** (own socket, own handover) | yes | no |
| `deploy/voice-record.mjs` | yes | yes | **yes** |

`voice-record.mjs` loads the shipped `vyne-live.js` and `vyne-live-interview.js`
from disk into a vm, shims the browser around them (AudioContext, mic,
localStorage, the grant fetch), and points them at the real Live socket. Every
sample the page would have played is written to a stereo WAV — **L = the
interviewer, R = the interviewee**, on one timeline — so a handover gap, a
stop-go choke or a dead tenth minute is something you hear rather than infer.
It opens with the same short trigger through the same `open()` the page uses.

`--offline` runs the whole thing against a local stand-in for Gemini: no key,
no quota, no network, and a `goAway` on a timer so the handover path still
runs. It exists because this harness has a fixture problem by construction —
a broken rig and a broken product produce identical output, and that mistake
has already been made three times (a tone instead of speech, a hardcoded TTS
model, a mute uplink). `run-voice-record.sh` runs the offline check first and
refuses to start a real run if it fails.

The offline check earned its keep immediately: it caught the harness enqueuing
two answers after a handover, which backed the uplink up and produced a clean
8.4 s "latency degradation" that was entirely the rig. Answers are now gated on
the uplink having actually drained, and reply latency is timed from the drain
rather than from a timer that assumes it.

The grant is minted inside the harness in the shape `/api/voice/live-session`
returns, so the budget hold, concurrency cap and `renewalOf` exemption are NOT
under test — deliberately, so a cap refusal can never be mistaken for a voice
fault. Test those with a real interview.

## 5.34.43 — the handover nudge is a trigger, and a fragment is not a failure

The 90-minute trace carried ELEVEN `!!! MUTE TURN` lines. Every one at reply 1
or 2 of a renewed connection; never mid-conversation. Two different things were
wrong, one in the product and one in the instrument.

### The product: we asked for a text reply and got one
The handover nudge was 245 characters of four-clause instruction, and it said
"In one short sentence **say you are still here**". Three of the eleven mute
turns are the literal text `"I am still here."`

This file already contained the answer, written above `_openingLine` in
interview_agent.html: *"Sending the long instruction as a USER turn made the
native-audio model reply in TEXT instead of speaking, so the interview opened
silently. We now send only a SHORT trigger."* That fix landed on the OPENING in
5.34.11 and was never applied to the handover — the one place the same user
turn is sent, nine times in a 90-minute interview.

The nudge is now `"Please continue."` (resumed) / `"Please continue with your
next question."` (fresh). No acknowledgement requested, no re-statement of what
a resumed session already has. The persona governs not re-greeting;
buildLiveContext carries the transcript into a fresh session.

### The instrument: seven of the eleven were never failures
Seven were SEVEN characters — "So most", "What is" — a transcription tail
flushed at a connection boundary, reported with the same `!!!` prefix as a real
fault. An instrument that cries wolf is worse than no instrument, because the
whole value of this trace is that `!!!` means something. `MUTE_TEXT_MIN_CHARS`
(default 12, `VYNE_MUTE_TEXT_MIN_CHARS` to tune) now separates the two: below
the floor it is still recorded, quietly, and never spoken aloud.

### How to tell whether this worked
The baseline is **11 mute turns across 9 handovers = 1.2 per handover** on
5.34.42. A short run cannot measure that — two handovers predict ~2 events,
which is noise. Measure it on the next 90-minute run, and expect the fragment
class to vanish outright (instrument) and the "I am still here" class to stop
(product). Five tests pin both halves, including that the nudge never again
contains the word "say".

## 5.34.44 — the nudge revert, measured; and a socket error stops killing interviews

### The nudge: 5.34.43 was wrong, and the 90-minute run proved it
Same tier, same model, same nine handovers, back to back:

| | 5.34.42 (long instruction) | 5.34.43 (short trigger) |
|---|---|---|
| text-only replies at handovers | **3** | **18** |
| what they said | "I am still here." | `"Please continue."` ×18 |
| where | replyNo 1 of a renewal | replyNo 1, 2, 3 of every renewal |

Six times worse. The model was **echoing the nudge back** instead of acting on
it. The 5.34.43 reasoning — "the long instruction is what makes it answer in
text, so shorten it like the opening" — had the mechanism backwards. Length was
never the problem. `"Please begin the interview now"` works because it names an
ACTION; `"Please continue"` names nothing, so there is nothing to do with it but
repeat it. The long form tells the model what to say and then what to do next,
which is precisely why it does not echo.

5.34.44 restores the 5.34.42 wording verbatim, with the evidence recorded in
the code. **Do not shorten it again without a 90-minute run to compare against**
— the archives are `voice-runs/tier1-90min.*` (long form, 3) and
`voice-runs/tier1-90min-v43.*` (short trigger, 20).

The two tests that pinned the short trigger have been DELETED, not adapted. A
test defending an answer the evidence has overturned is worse than no test.
5.34.43's other half — the `MUTE_TEXT_MIN_CHARS` fragment filter — measured
well (15 transcript tails correctly reclassified, zero false `!!!` lines) and is
kept, with its tests.

### The socket error: one missing string cost whole interviews
`isRenewable()` listed `'error'`. `vyne-live.js` raises **`'live_socket_error'`**.
No match — so every socket error fell straight through to "not renewable" and
ended the live path outright, with the entire renewal apparatus (resumption
handle, backoff, concurrency exemption, the 5.34.42 mute-resume watchdog)
sitting unused beside it.

Found when a test run died at minute five: the laptop slept, and on waking the
socket was long dead. The interview never came back. In production that is an
interviewee who shut their lid for lunch or lost signal in a lift, returning to
a dead line — answers safe, voice gone for good.

Four tests: the nudge is not a bare imperative and still contains its
instruction; a socket error renews and presents the resumption handle; a
deliberate stop is still never renewed; and the reason string the renewal path
checks is the one the transport actually raises.

### Measured for the record — the 5.34.43 90-minute run
346 replies, 9 handovers, 0 recoveries, p50 1.4s, p90 2.1s, p99 3.0s,
**max 4.4s, 0 of 346 over five seconds**, halves 1.7s → 1.4s. The best latency
profile the project has produced; almost certainly run-to-run variance rather
than anything 5.34.43 did, and claimed as nothing more.

## 5.34.45 — the interviewee is finally told what happens to their voice

`privacy.html` and `dpa.html` described voice handling accurately — third-party
providers named, transcription for scoring explained — and **neither was linked
from anything the interviewee ever saw**. The only notice on that path was on
the CONSULTANT's setup screen (the one that asks for an Anthropic API key):
*"the agent speaks questions aloud and listens to your responses."*

So the person whose voice was being processed was never shown what happened to
it. That gap existed in every interview conducted to date.

### Why it is not just courtesy
Several US states — California, Illinois, Florida, Pennsylvania, Washington,
Massachusetts — require ALL parties to consent before a conversation is
intercepted, and the statutes are not limited to saved audio: the federal
definition is the *"aural or other acquisition of the contents"* through a
device, which a transcript plainly is. The active CIPA litigation turns almost
entirely on whether an **undisclosed third party** received the contents. Ours
is Google, in real time — and "we do not keep a recording" does not answer that,
because the audio still leaves the browser. The disclosure therefore names it.

### What shipped
- `consentBlock()` on the interviewee's own `renderWelcome()` overlay: a
  "Transcribed, not recorded" panel, the wording below, a link to privacy.html,
  and a checkbox that must be ticked before any start button enables.
- Every start path in renderWelcome is `data-needs-consent` and ships
  `disabled`. `renderPaused()`'s Resume is deliberately NOT gated — it unpauses
  an interview whose consent is already recorded.
- `S.consent = { acknowledgedAt, version, text }`, saved with the session, so
  the wording actually shown is evidenced rather than assumed.
- A persistent "Transcribed, not recorded" pill in the interview header, with
  the full explanation on hover.

### The wording, and why not the shorter version
Asked for was *"transcribed not recorded for score reasoning"*. Kept the
headline, changed the rest. "Not recorded" alone invites the reading "nothing
leaves my browser", which is false and is precisely the inference the wiretap
claims are built on; and "score reasoning" is internal vocabulary. Shipped:

> This interview is transcribed, not recorded. Your voice is turned into text as
> you speak, and the audio is not kept. The transcript is stored so your answers
> can be explained — it is what lets us show why each readiness score was given.
> Speech is processed by a third-party AI provider (Google) to produce that text.
> Your consulting team can read the transcript; it is not shared outside the
> engagement.

Seven static tests in `intervieweeConsent.test.ts` pin all of it, including that
every start button on the welcome screen carries the gate — a new start path
added without it fails the release gate.

**NOT LEGAL ADVICE.** This closes an obvious gap; it is not a compliance
opinion. Counsel should be asked one specific question: does this flow satisfy
all-party-consent requirements given that audio transits a third-party provider,
when the interviewee may sit in any jurisdiction?

## 5.34.46 — a dead network is not a refusal

Wi-Fi was pulled four minutes into a live run. The trace, end to end, in 36
milliseconds:

```
+240534  ws ERROR
+240542  session.stop(live_socket_error)
+240543  LiveInterview: renewing lapsed session      <- 5.34.44 fired, correctly
+240569  grant REFUSED by our server                 <- network still down
+240570  LiveInterview: renewal FAILED — live path is over
```

5.34.44 made a socket error renewable, which was right. The renewal then died
26 ms later minting a grant over the same dead network, landed on
`renew_failed`, and `renew_failed` is in DELIBERATE — permanent. **5.34.44
moved the failure one step downstream and stopped there.**

### Two bugs, and the second was hiding
**Every renewal failure was treated identically.** A refusal (our concurrency
cap, budget, 401) is terminal and retrying only burns the cap. A transport
failure (fetch threw, 5xx, no status) is an interviewee who shut a laptop lid
or walked into a lift. `isTransientRenewFailure()` now separates them:
transport retries on a bounded backoff (4s doubling to 20s, six attempts ≈ 90 s
of coverage), refusals stay terminal. A just-dead socket also gets
`SOCKET_SETTLE_MS` (1.5 s) before the first mint, rather than firing into a
socket that has only just died.

**The interview ended TWICE and the first ending disarmed the recovery.** Look
again at the run output: `interview ENDED: mint_failed` *then*
`interview ENDED: renew_failed`. The replacement session's own start failure
called `stop('mint_failed')`, which re-entered the interview's `onEnded`
handler with a non-renewable reason, set `stopped = true`, and fired onEnded —
all BEFORE the renewal's catch ran. The catch then found the interview already
declared over and skipped the retry it was about to make. `self._renewing` now
gates that handler: while a renewal is in flight it owns the outcome, and the
dying replacement does not get a vote.

The retry re-enters ONE named chain (`attemptRenewal`), so the resumption
handle, the nudge and the 5.34.42 mute-resume watchdog all still apply on a
retry. A second parallel reconnect path would have drifted from this one within
a release.

### Still unverified
The 14-minute run died at four minutes, before the handover — so **the 5.34.44
nudge revert is still unmeasured against the real API**. The next clean
14-minute run answers it; the archived comparison is `voice-runs/tier1-90min.*`
(long form, 3 mute turns / 9 handovers) versus `tier1-90min-v43.*` (short
trigger, 20).

## v5.34.47 — the retry waits once, and the log says so

Two defects, both found by reading the v5.34.46 Wi-Fi-drop trace against the
recording rather than by a failing test. Neither broke the interview; both made
recovery slower than designed and the evidence harder to trust. Fixed before
the final 90-minute run so that run's numbers mean something.

### 1. The backoff was double-counted

`onRenewalFail` scheduled the retry with `setTimeout(..., backoff)`, and then
`attemptRenewal()` computed `retryWaitMs` from the same retry streak and waited
*again* before minting. Every retry therefore waited twice as long as the trace
said it did:

| retry | logged | actual |
|---|---|---|
| 1 | 4 s | 8 s |
| 2 | 8 s | 16 s |
| 3 | 16 s | 32 s |

The measured consequence: the 58-second recovery in
`voice-runs/v46-14min-wifi-drop.*` should have been about 28 seconds. Worse
than the lost half-minute, **the trace disagreed with the recording**, which is
the one thing this harness exists to prevent.

The wait is now computed in exactly one place, `renewWaitMs()`, read both by
`attemptRenewal()` and by the line that logs `inMs`. The retry calls
`attemptRenewal()` directly — there is no timer wrapped around it. A static
test asserts `}, backoff);` no longer appears in the file, so the timer cannot
quietly come back.

Moving the wait inside `attemptRenewal()` moved the "did the interview end
while we were waiting?" guard with it. It now rejects with `renew_aborted`,
which `onRenewalFail` recognises and returns on silently — otherwise a `stop()`
during a backoff would have fired `onEnded('renew_failed')` on top of the
ending that had already happened. That is the same class of bug as the
`_renewing` double-ending fixed in .46, and it is covered by its own test.

### 2. The recorder called every retry a new handover

`onRenewing` fires once per *attempt*, and a transport retry re-enters it with
reason `reconnecting`. So one handover with three retries printed:

```
— handover #1 starting (this is the ~10-minute one) —
— handover #1 starting (this is the ~10-minute one) —
— handover #1 starting (this is the ~10-minute one) —
— handover #1 starting (this is the ~10-minute one) —
```

Four lines, one handover. `deploy/voice-record.mjs` now counts the handover on
the first attempt only and labels the rest `still reconnecting (retry N)`, and
`onRenewed` reports how many retries it took. The final run's log is meant to
be read by someone who was not watching it happen.

### Also fixed: 13 tests that had silently stopped running

`backend/test/renameClientUI.test.ts` had duplicated its own imports —
`readFileSync`, `dirname`, `join` and `fileURLToPath` each imported twice — so
esbuild refused to transform the file and vitest reported it as a failed
*suite* containing zero tests. Almost certainly collateral from the nested
`vyne-saas/vyne-saas/` folder merge earlier in the session. The file parses
again and its 13 tests are back in the gate: **1,049 passing, 0 failing,
typecheck clean.**

### What still has to be proved on the real API

The 90-minute proof on record is 5.34.42's code. Versions .44, .46 and .47 all
changed the **renewal path**, which fires once or twice in a fourteen-minute
run and **nine times in ninety**. That is why one more full run is justified
before this is called done. Pass criteria, fixed in advance:

| | target | where the number comes from |
|---|---|---|
| handovers | ≥ 9, 0 needing recovery | .42 baseline |
| `"Please continue."` echoes | 0 | the .43 regression |
| mute turns | ≤ 3 | .42 measured 3 |
| re-greetings after a handover | 0 | .45 risk |
| p50 latency | ≤ 2 s | .42 was 1.3 s |
| first half vs second half | flat | no degradation |
| ends because | the 90-minute limit, not a failure | |

Run it clean — no deliberate Wi-Fi interference. The unplanned outage during
the .46 run already proved that path; mixing a forced outage into this run
makes every latency number ambiguous.

### Fault injection — proving the recovery path without waiting for bad luck

Everything .47 changed sits on the failure path. A clean run of any length
executes the renewal path but never those lines: a ninety-minute run crosses
nine handovers and zero retries. The .46 backoff bug was found only because a
real Wi-Fi drop happened to occur during a recording. That is luck, not a test.

`deploy/voice-record.mjs` now takes `--offline-fail-mints N` (offline only). It
refuses the next N grants **after** the opening one with a bare 500 and no
error code — the shape `isTransientRenewFailure()` classifies as transport, so
the retry path runs for real. The attempt times are recorded and judged in the
verdict against the schedule the shipped constants describe:

```
fault injection:  3 mint(s) refused, 3 retry gap(s) measured
  retry 1: waited 4.0s, expected ~4.0s  ok
  retry 2: waited 8.0s, expected ~8.0s  ok
  retry 3: waited 16.0s, expected ~16.0s  ok
  recovered: yes — the interview continued
  handover label: 1 handover(s) counted across 4 attempt(s)  ok
  PASS
```

**The negative control matters more than the pass.** The .46 double-count was
put back and the same check re-run:

```
  retry 1: waited 8.0s, expected ~4.0s  << WRONG
  retry 2: waited 16.0s, expected ~8.0s  << WRONG
  retry 3: waited 32.0s, expected ~16.0s  << WRONG
  FAIL
```

Total recovery 58.1 s against 30.1 s on .47 — the same 58 seconds the real
Wi-Fi drop cost in `voice-runs/v46-14min-wifi-drop.*`. So the check reproduces
the actual production event, and it fails on the code that had the bug. A
green result from it is evidence rather than an absence of evidence.

`deploy/run-voice-record.sh` now runs it as step 2 of 4, before any key is read
or any quota is spent. Two minutes, no cost. If the retry schedule regresses,
the real run never starts.

### Revised test plan — 35 minutes instead of 90

The 90-minute run was the wrong recommendation for .47 and is withdrawn. It
would have proved endurance, which nothing since .42 has changed, while
executing none of the lines .47 touched.

| | cost | what it proves |
|---|---|---|
| fault injection (2 min, offline) | none | the retry schedule, the recovery, the handover label — **the only test of .47** |
| 30-minute real run | ~$0.33 | three handovers, echoes, mute turns, re-greetings, latency flatness; crosses context compression (trigger 25,600 tokens ≈ 8.5 min of two-way audio) |

What 35 minutes does **not** buy: nine handovers in one session, and the
behaviour at minute 85. Handover count and compression coverage pull against
each other — shortening the minted token to force handovers every few minutes
keeps each session below the compression trigger. Buying both at once is
precisely what the ninety minutes is for. Spend it when there is a reason to
quote an endurance number, not as a regression test.

## v5.34.48 — the client invoice was twenty times the real cost

### What was measured

Production, 2026-09-12, one tenant:

```
 task                      | count |   tin   |  tout   |   usd
---------------------------+-------+---------+---------+----------
 live_session              |    42 |  150620 |    9399 |   0.3386
 live_session_hold         |    92 |  810000 |  810000 |  17.0100
 live_session_hold_release |    62 | -540000 | -540000 | -11.3400
 live_session_refund       |    10 | -675000 | -675000 | -14.1750
 live_session_reserve      |    13 |  877500 |  877500 |  15.5925
```

Ninety-two holds, sixty-two releases. **36 holds were never released, carrying
$6.62**, against $0.34 of metered actual consumption. Billing sums this table,
so the voice line on that firm's client statement was roughly twentyfold what
the sessions cost.

### Why

A live session reserves its worst case at mint and the BROWSER releases it, by
POSTing `/api/voice/live-session/close`. That POST is fire-and-forget —
`keepalive: true`, and a `.catch(function () {})` that swallows every failure.
A killed tab, a network drop at the wrong instant, or any server-side refusal
strands the hold permanently, and neither end ever knows. A financial record
cannot depend on a browser surviving long enough to report.

This is the same failure `reconcileSession`'s own comment records fixing once —
*"the client was invoiced for a worst-case estimate instead of what actually
happened"* — arriving by a different route. Not a partial refund this time, but
a refund that never comes.

Note the spend caps were NOT affected: `excludedSessionsCte` already ages
unreleased holds out of the cap window (v5.32.63/.83). Billing has no such
logic, which is why the invoice was wrong while the caps were right.

### The fix

`backend/src/llm/sweepStaleHolds.sql` releases any hold older than
`MAX_SESSION_SECONDS + 600s` that has no release row, using the **stored** hold
amounts. It runs from `sweepStaleHolds.ts` at the top of `admitLiveSession`,
inside the transaction that admission already holds.

That placement is the design, not a convenience: the sweep lands immediately
before the concurrency count and the spend-cap check, both of which read sums
over `usage_events`. No new endpoint, no new authenticated surface, no Cloud
Scheduler to provision and later discover has been failing silently. A firm
that runs interviews cleans itself up the next time it runs one.

**It does not invent an actual-usage row for a swept session.** We never
learned what those sessions cost, and a server-side estimate would put a
number on a client invoice that nothing measured. Releasing and recording
nothing undercounts — the session did cost something — and an honest
undercount is the right side to err on against a fabricated charge.

### Tested against real Postgres, not a mock

Everything that makes this safe is a database property — FORCE row-level
security, migration 015's partial unique index, `ON CONFLICT DO NOTHING`. A
mocked `query()` would assert a SQL string and prove none of it. So
`backend/test/sweepStaleHolds.test.ts` runs against a real server
(`RLS_TEST=1`), nine cases: the stale hold goes, a hold that could still be a
running interview stays, an already-released hold is not released twice, a
second run changes nothing, two holds for one session yield one release,
another firm's rows are untouched, an unset tenant sweeps nothing rather than
everything, and a failure leaves the transaction usable.

**Negative controls, because a test that cannot fail proves nothing:**

- Remove the SAVEPOINT → `current transaction is aborted, commands ignored
  until end of transaction block`, and admission would have died with it. A
  plain try/catch is not sufficient inside an open transaction; this is why.
- Remove `DISTINCT ON` → **the test still passed.** `ON CONFLICT DO NOTHING`
  resolves the duplicate within the statement as well as against committed
  rows. The SQL comment claiming DISTINCT ON was the guarantee was wrong and
  has been corrected; it stays only to make the choice of which hold gets
  mirrored deterministic.

### Backfill for the 36 already stranded

`deploy/backfill_stale_holds.sql`. Prints the voice-line total before and
after. Verified on a seeded database: $5.70 → $0.03, and a second run inserts
nothing.

```
SET app.tenant_id = '<tenant uuid>';
\i deploy/backfill_stale_holds.sql
```

`usage_events` is FORCE RLS, so with no tenant set it quietly does nothing —
which looks exactly like success. Set it.

### Open, found while testing — NOT caused by this release

With `RLS_TEST=1` the suite runs 1,217 tests instead of 1,052. **Thirteen of
them fail**, in `interviewIdentity.test.ts` and
`followupAgendaConfidentiality.test.ts`, on a freshly created database — so not
stale data. Symptoms are `409` where `201` is expected on invite creation, and
one round's saved state visible where it should be absent. These are skipped by
default (`RLS_TEST` unset), so they have most likely not run in a long time and
may simply be stale relative to the code. **That is a guess.** Either they are
stale, or there is a real interview-identity bug, and the difference matters
enough to find out deliberately rather than leave skipped.

### Confirmed in production, same day

After deploying .48, a single live session's admission swept the backlog
unprompted:

```
                         before      after
 live_session_hold          92         92     (unchanged — no new sessions)
 live_session_hold_release  62         88     (+26, releases only)
 live_session               42         42     (unchanged — no new actuals)
 orphaned holds             36         10
 voice line                $7.43      $2.70
```

Releases appearing with no new holds and no new actuals is the sweeper's
signature, and it means the mechanism works end to end in production without
the backfill being run at all.

The 10 that survived are **not** recent. They are ~31 days old and have
`session_id IS NULL` — written before migration 015 added the column. The
statement requires a session id deliberately: without one there is nothing to
pair a release to and nothing for the unique index to make idempotent. So it
skipped them correctly. The same is true of the older `live_session_reserve` /
`live_session_refund` pair, 13 and 10 rows, also all NULL.

That residue is a closed pocket — it cannot grow, since every row written since
015 carries a session id — worth about $2.36. It is cleared by
`deploy/correct_legacy_live_ledger.sql`, which writes ONE correcting row under
a fixed session id (`legacy-pre015-correction`) so the unique index makes a
second run a no-op. Verified on a seeded replica of the exact production shape:
$2.7002 → $0.3386, which is precisely the metered actual consumption, and a
second run inserts nothing.

### Two flaws found in the TEST SETUP, not the code

Worth recording because both would have produced false confidence.

**The admin role bypasses RLS.** The local test role was created SUPERUSER, and
superusers ignore row-level security entirely — so a cross-tenant check written
against that connection summed both firms and still "passed". The repo's own
convention already handles this (billing.test.ts uses a separate `vyne_app`
connection for RLS behaviour and the admin one only for fixtures). The header
of `sweepStaleHolds.test.ts` now states plainly that the isolation it asserts
comes from the statement's explicit `tenant_id` predicate and NOT from the
policy — which is the safer design anyway: the statement stays correct even
when the policy is not applying.

**The before/after readings leaned on RLS.** Both operator scripts totalled
`WHERE provider = 'gemini-live'` with no tenant clause. Run by an operator
connected as `postgres` — plausible, since that is the role `gcloud sql
connect` reaches for first — that sums every firm, and a correct correction
looks like it removed far too much. Both scripts now filter by tenant
explicitly. Verified by running the correction as a superuser with two tenants
present: $15.5922 → $0.0000 for the target firm, the other untouched at
$19.9998.

## v5.34.49 — the other half of the voice bill

v5.34.48 removed charges for sessions that never happened. This one counts the
sessions that did.

### The number that gave it away

With the phantom holds gone the voice line read $0.3386 — across 42 sessions,
**150,620 input tokens against 9,399 output**. Both directions are audio. An
interviewer speaks about as much as an interviewee, and output audio is the
EXPENSIVE direction. Output at 1.6% of input is not a cheap session; it is a
figure counting the text transcript and missing the speech.

### What the frontend was doing

```js
self.usage.tokensIn  = f.usage.promptTokenCount   || self.usage.tokensIn;
self.usage.tokensOut = f.usage.responseTokenCount || self.usage.tokensOut;
```

Two defects, both undercounting:

**It reads only the two scalars.** `usageMetadata` also carries
`promptTokensDetails[]` and `responseTokensDetails[]`, each `{modality,
tokenCount}`. For native audio the audio tokens may be reported only there.
`_recordUsage()` now takes `max(scalar, sum(details))` per direction —
deliberately max rather than sum: if the scalar is already the aggregate, max
returns it unchanged and nothing double-counts; if it excludes the audio, max
picks up the truer figure. It can never exceed what Google itself reported.

**It assigned rather than accumulated,** so the LAST frame won. Whether
usageMetadata is cumulative per session or scoped to a turn is not something
this code should assume, and it is the difference between a correct invoice and
one an order of magnitude light. Monotonic max is correct under either reading.

### The link to .48

A third consequence, found by the negative control rather than by looking: the
old line assigned whatever arrived. A non-numeric `promptTokenCount` was
therefore sent verbatim to `/close`, where `LiveCloseBody` requires
`z.number().int()` — so the request 400s, the frontend's
`.catch(function () {})` swallows it, and **the hold is stranded permanently**.
That is a mechanism by which .48's orphans could be created. It is not proof
that it created those 36; it is proof the old code made it possible and the new
code cannot.

### Honest about what is still inferred

The field set is inferred from a token RATIO, not from a captured frame. The
30-minute harness run recorded no `usageMetadata` at all, and the old trace
logged only the two scalars — which is precisely how a 1.6% output figure went
unnoticed across 42 sessions. So the trace now dumps the WHOLE object once per
session, and the frame line carries both details arrays. **The next real
interview through the app settles it**: pull `vyneLiveLogDump()` and read
`usageMetadata (full shape, first frame of this session)`. If the details
arrays turn out to be empty and the scalars are already aggregates, the max()
is a no-op and no harm is done — but we will know rather than infer.

### Tests

Six behavioural cases in `liveTurnOwnership.test.ts`, driven by real frames at
the socket: details-only audio counted, no double-count when the scalar is the
aggregate, a later smaller frame cannot erase an earlier larger one, a zero
frame leaves a real count alone, malformed usage never throws, and the close
beacon sends what was counted.

**Negative control: four of the six fail on the old code**, including the
malformed-usage case — which is how the `/close` stranding mechanism above was
found.

## BYOK — the free-tier detection question, half answered

`deploy/byok-probe.mjs`, run against the production (BILLED) AI Studio key,
2026-09-12:

```
  generateContent            HTTP 200
  models.list                HTTP 200 — 55 models visible
    live/native-audio        gemini-3.5-transcribe-live,
                             gemini-2.5-flash-native-audio-latest,

```

**One avenue is definitively closed.** Google returns no
`x-ratelimit-*` headers, so tier cannot be read from response metadata.

**Two candidate signals remain, and both need an UNBILLED key to test:**

1. `auth_tokens`. If a free key is refused there, that is a clean gate — and

2. The model list. 55 models with six live/native-audio entries is what a

always been: an operator's assertion via `GEMINI_PAID=1`, trusted by

is defensible while the key is ours. It is NOT defensible as a client-facing
check, because the assertion would come from the party who benefits from
getting it wrong.

**If no signal separates the two**, the honest options are BYOC (a client GCP
project on Vertex, where the no-training position is contractual rather than
inferred) or a recorded client attestation with the consent text saying plainly
that it IS an attestation. Do not ship a checkbox that reads as verification.

### Answered: there is no signal

The same probe against an UNBILLED key, created in a fresh project with no
billing linked, 2026-09-12:

```
  generateContent            HTTP 200          (billed: 200)
  models.list                HTTP 200, 55      (billed: 200, 55)
    live/native-audio        the same six      (billed: the same six)
  auth_tokens                HTTP 200          (billed: 200)
  rate-limit headers         NONE              (billed: NONE)
```

Byte-for-byte the same capability surface. **A free-tier key cannot be
distinguished from a billed one at save time.** So "reject free-tier keys"
is not implementable as a check, and must not be shipped as one.

**Correction to a belief held across this session and in the code comments:**
free-tier keys are NOT refused by `auth_tokens`. Google mints a Live ephemeral
token for an unbilled key without complaint. `live_free_tier_blocked` is
entirely self-imposed through `GEMINI_PAID=1`; nothing upstream enforces it.
The policy is still right — free-tier content may be used for product
improvement, and an interview transcript is the most confidential thing here —
but it is OUR policy, not Google's gate, and the comments should stop implying
otherwise.

Caveat on scope: the probe makes three calls. Free tier differs under LOAD
(RPM/RPD ceilings), not at the capability surface. Detecting tier by
deliberately exhausting a client's quota is not a check worth having.

### What this forces

BYOK and "free pilots that cost the client nothing" are mutually exclusive with
a no-training guarantee:

- **BYOC** (client GCP project on Vertex) keeps no-training contractual, but
  requires the client to create a project and enable billing — which is exactly
  the thing a free pilot is avoiding.
- **Attestation** keeps pilots free, but the guarantee becomes the client's
  word, and a pilot client has every incentive to use a free key.

**The part that decides it is not whose card is charged.** The consent gate
shipped in v5.34.45 tells the interviewee their transcript "is not shared
outside the engagement." On a free-tier key that may not be true — Google may
use the content for product improvement. The interviewee is the person whose
words are at stake and is NOT the party choosing the key.

So if attestation is chosen, two things are non-negotiable:

1. A BYOK tenant's interviewee consent text must say what is actually true for
   that tenant, and the interviewee must see it before consenting.
2. The stored flag must be named for what it is — `paid_tier_attested`, with
   who attested and when — never `paid_tier`. A field name that overstates its
   evidence is how a checkbox becomes "the system verified it" in someone's
   memory a year later.

## v5.34.50 — BYOK foundation

Slice one of three. Schema, key storage, key probing. **Nothing in the request
path changes**: no adapter resolution, no routing, no UI. A tenant with no BYOK
row behaves exactly as before, because no code reads these columns yet.

### Migration 030

`tenants` gains `byok_provider`, `byok_secret_name`, `byok_key_hint`,
`byok_status`, `byok_verified_at`, `byok_probe`, `byok_paid_tier_attested`,
`byok_attested_by`, `byok_attested_at`, `byok_attestation_text`. Plus
`byok_events`, an append-only trail of who attached, rotated or disabled a key.

**The key itself is never in the database** — only the Secret Manager resource
name. A database backup is copied, restored into staging, handed to a
contractor and attached to a support ticket; a client credential must not
travel with it.

Three CHECK constraints, all verified against real Postgres:

- `byok_active_requires_attestation` — a key cannot be ACTIVE without a named
  attester, a timestamp, and a copy of the text they were shown. In the
  database rather than the route, because there will be more than one way to
  write this row before long (an admin tool, a migration, a support fix) and

- `byok_provider_known` — `gemini-aistudio` only. Vertex authenticates with

  BYOK row would be a promise the router could not keep.
- `byok_status_known` — active / disabled / failed.

`byok_events` is granted SELECT and INSERT to `vyne_app` and nothing else. An
audit trail the application can edit is not one.

### Naming, which is the whole point

`byok_paid_tier_attested`, never `byok_paid_tier`. `byok_probe` holds what the
probe observed, not a verdict derived from it. `verifyKey.ts` has no
`paidTier`, `tier`, `accepted` or `verified` field, and a test asserts it never
grows one.

This is not fussiness. The probe proved a billed key and an unbilled key are
indistinguishable — so any field named as though the tier were checked would be
a guess wearing the clothes of a check, and a year from now someone would rely
on it in a conversation about a client's confidential data.

### What the probe IS for

Refusing a key that cannot do the job: no text generation, no visible
native-audio model, or no Live ephemeral token. Those fail mid-interview, in
front of a client executive, and the settings screen is a much better place to
find out. `keyIsUsable()` is explicit that this is a capability check.

### Secret Manager over REST

Via `google-auth-library`, already a dependency for the Vertex adapters, rather
than `@google-cloud/secret-manager` — which would pull gRPC and a large tree
into the image for four calls. Keys are cached five minutes: no cache means a
network round trip on every generate(), an unbounded one means a revoked key
works forever. Writes and disables evict immediately, so a rotation performed
here takes effect at once; the stale window only covers a change made in the
console or by another instance.

### Tests — 27, negative-controlled

21 unit (storage, cache expiry, rotation eviction, failure messages that name
the failure without naming the key, probe evidence, capability refusals) and 6
against real Postgres for the constraints.

- Drop `byok_active_requires_attestation` → two tests fail. The constraint is
  doing the work, not the test.
- One test failed first time by matching the migration's own COMMENT explaining
  why `byok_paid_tier` was rejected. Fixed by stripping comment lines before
  asserting — the same trap as the `readFileSync` check in

## v5.34.52 — the accumulator, which is what was actually wrong

### The measurement

Rony's interview (Nestlé), session `55111401`, through the app on .50:

```
  session_secs    590
  tokens_out      367      about 15 seconds of speech, in a ten-minute segment
  tokens_in     9,705      the PEAK context size of one turn, not consumption
  usd          0.0170      against roughly $0.20 of honest usage
```

Audio tokenises at ~25 tokens/second. Jack spoke for minutes, not fifteen
seconds. **Roughly a thirteenfold undercount, on the most expensive call the
product makes.**

### The captured frame, which corrected the previous release

```json
{"promptTokenCount":2230,"responseTokenCount":249,"totalTokenCount":2479,
 "promptTokensDetails":[{"modality":"TEXT","tokenCount":1946},
                        {"modality":"AUDIO","tokenCount":259}],
 "responseTokensDetails":[{"modality":"AUDIO","tokenCount":249}]}
```

`responseTokenCount` EQUALS its audio detail. The scalars are already the
aggregates, so **v5.34.49's `max(scalar, detailsSum)` was a harmless no-op and
never the fix.** The details-array theory in that release's notes was wrong;
the entry is corrected rather than deleted, because the reasoning that produced
it is the reason the right question got asked.

Note also that input is dominated by TEXT (1,946 against 259 of audio): that is
the persona and conversation context, re-counted each turn, not the
interviewee's voice.

### What changed

Usage is **maxed within a turn and summed across turns**, banked once at
`turnComplete`.

.49 replaced "take the last frame" with "take the largest frame", reasoning
that monotonic max was right whether the field was cumulative or per-turn. It
is not: for a per-turn field, max records the single biggest turn and calls it
the session. That is the 367.

Banking at the turn boundary rather than adding every frame is deliberate.
Whether Google emits usage once per turn or repeatedly within a turn carrying a
running total is STILL not established — one frame cannot say. Max-within-turn,
sum-across-turns is correct under both readings, and summing every frame would
double-count under the second. `stop()` flushes any open turn, because a
handover or a hang-up lands mid-turn more often than not.

### Why it took three releases to find

The frame classifier returned before the standalone `usageMetadata` branch, so
usage riding on a frame that also carried audio or a transcript never reached
the trace — only the rare frame that arrived alone. A whole session's usage was
invisible, which is exactly why per-turn versus cumulative could not be settled
and the accumulator stayed wrong through .48 and .49. The classifier now
surfaces it inline.

### Tests

Six new cases: three turns add up rather than reporting the largest; several
frames inside one turn bank once; a session ending mid-turn still bills that
turn; a turn is never banked twice; a turn with no usage banks nothing; and
usage riding on a mixed frame reaches the trace.

**Negative control: restore .49's session-wide max and four of them fail.**

The four .49 tests were repointed rather than deleted — they guard real
behaviours (details arrays, no double-count, zero frames, the close beacon)
that are still worth guarding; they simply asserted the wrong accumulator.

### What to expect after deploying

Voice costs on the client statement will RISE, by roughly an order of
magnitude, and that is the correction — those interviews always cost that. It
is also the opposite direction to v5.34.48, which removed $6.62 of charges for
sessions that never happened. Both were wrong; they were wrong in opposite
directions, and the netting is coincidence rather than cancellation.

## v5.34.53 — BYOK at the CLIENT grain, per provider

### 030's grain was wrong, and is dropped rather than deprecated

030 put the key on `tenants`: one key per consulting firm. That is not how the
business works. A firm runs engagements for several clients at once, and it is
the CLIENT's pilot that should pay for the client's interviews. A firm-wide key
bills Nestlé's interviews to whoever set the key up.

There is no `clients` table — a client is `engagements.client_name`, normalised
to `client_norm`, which is already the grain `usage_events` attributes cost to
and `client_assignments` scopes access by. So `byok_keys` keys on
`(tenant_id, client_norm, provider)`.

The 030 columns are DROPPED. Nothing ever wrote them — verified with a grep
across `backend/src` before dropping, which returns only a doc comment. Leaving
a constrained, unused set of columns on `tenants` would be a trap for whoever
reads the schema next and reasonably concludes firm-level BYOK exists.

### Per provider, which 030 did not anticipate

"Gemini for the voice interviews, Claude for the strategy deck" is a reasonable
client ask, and those are different vendors with different credentials — a
Google AI Studio key cannot pay for Claude. So "does this client bring their own
key" is one question PER PROVIDER, and the answers can differ.

`byok_key_provider_known` allows `gemini-aistudio` and `anthropic-api`. Both
Vertex providers are excluded on purpose: Vertex authenticates with
service-account credentials, not an API key, so a Vertex row would be a promise
the router cannot keep.

### Three states, and the middle one is the common case

For any (client, provider):

- **active** — the client's credential pays, and the charge lands on their bill.
- **no row / pending / failed / disabled** — the platform credential pays, the
  call is metered to that client in `usage_events`, and it goes on the invoice
  the firm sends. This is the realistic default: supplying a key means a Google
  Cloud account with billing enabled, and a client running a free pilot is not
  opening one.

A lapsed key therefore FALLS BACK rather than failing. An interview must never
die because a client's credential expired; the firm eats that cost until
someone fixes it, which is the right way round. Tested, with a negative control.

### The key never travels by email

`byok_invites` holds a single-use, expiring, hashed token. The Owner creates the
client as now, generates a link, and sends it; the client's administrator opens
it and pastes the key into a form that posts straight to the backend, which
probes it and writes it to Secret Manager. **The Owner never sees the value** —
only `ends in wxyz` and whether the capability checks passed.

A key pasted into a message lands in two inboxes, a mail server, someone's phone
and possibly a CRM, and it is the CLIENT's credential, not the consultant's to
route.

`byok_invites` is the one table deliberately NOT row-level-security scoped: the
client's administrator has no account and no tenant context, so the redeeming
route must find the row before any tenant is known. What protects it is a
high-entropy token, stored only as a hash, expiring, single-use.

### The attestation belongs to the client, not the Owner

`attested_by_email` is recorded alongside the user id, because the person who
can honestly attest that a key is billed is the client's administrator — who is
not a user of this application. An Owner attesting on the client's behalf is the
paperwork theatre the constraint exists to prevent.

### Tests — 10 at the client grain, against real Postgres

One client's key serves only that client; Gemini from the client with Claude on
the invoice; a client bringing both; a lapsed key falling back; rotation
replacing rather than duplicating; unattributed work never picking up a client
key; another firm's identically-named client getting nothing; audit rows naming
the attester; the database refusing a live key with no attestation; and the key
never appearing in the row.

**Negative controls:** drop the `status = 'active'` filter and the lapsed-key
test fails; remove the unattributed-work guard and that test fails. A third
control was written badly enough that it silently passed — the `sed` pattern did
not match, so nothing was changed and the "control" proved nothing. Re-run with
an assertion that the edit applied, at which point it failed correctly. Worth
recording: a negative control that cannot prove it modified anything is not a
control.

### Still ahead

Slice 2 remains the gateway resolution — `activeKeyFor()` exists and is tested,
but nothing calls it yet, and the failure to design against is credential bleed.
Then per-client ROUTING (which model serves which task for which client), which
is a separate axis from BYOK: routing decides the vendor, BYOK decides whose
credential pays, and a client can vary either independently.

## v5.34.54 — Claude on an API key, so a client can pay for their own decks

### The gap the question exposed

"Can a client provide their Google key AND their Anthropic key?" — the schema
said yes, the router could not deliver it.

`anthropic-vertex` authenticates with GCP Application Default Credentials.
There is nowhere in that flow to put a client's credential. So migration 031
allowed `anthropic-api` as a BYOK provider while no adapter of that name
existed — **the exact fault 031 excludes both Vertex providers for, committed
one constraint line later in the same file.**

### The adapter

`adapters/anthropicApi.ts` — Anthropic's own `/v1/messages`, `x-api-key` auth,
model in the BODY (Vertex puts it in the URL), pinned `anthropic-version`,
registered at boot so the name resolves for routing.

`freeTier: false`, and the asymmetry is worth stating: Anthropic has no free
tier — a key either has credit or it does not, and there is no
training-eligible tier to guard against. Google AI Studio is the opposite,
which is exactly why Gemini BYOK carries an attestation and this does not.

A 401 from a client's key surfaces its status so the caller can fall back to
the platform credential rather than stop; the key never appears in the message.

### Now answerable, per client

| | voice | decks and synthesis | who pays |
|---|---|---|---|
| client brings both keys | their Gemini key | their Anthropic key | entirely them |
| client brings Gemini only | their Gemini key | firm's Vertex | split: invoice the decks |
| client brings nothing | firm's key | firm's Vertex | invoice everything |

The middle row is the realistic default and needs no client involvement at all.

### The test that would have caught it

`every provider migration 031 allows now has an adapter that can serve it`
parses the CHECK constraint out of the migration, maps each allowed provider to
its factory, and asserts the factory is registered in `index.ts`. Negative
control: add `openai-api` to the constraint and it fails by name.

A BYOK row pointing at a provider the router cannot resolve is a promise to a
client that silently fails — and it took a question to find, not a test. Now a
test.

### Not yet wired

Nothing calls `activeKeyFor()`. The adapter is registered with the PLATFORM key
only. Slice 2 is still the per-request credential resolution, where the failure
to design against is credential bleed — one client's key serving another's call.

Three releases of schema with nothing visible. That was a fair thing to be

Three tests today failed on first run by matching a word inside the comment that

Recorded because it is a pattern, not three accidents.

## v5.34.56 — the frontend is tested by a browser now, not by the customer

### What was wrong with "frontend tests" in this repo

Every one of them was a string search over an HTML file. They catch a renamed
id and nothing else. They cannot tell you whether a tab switches, a fetch
fires, a table fills, or a submit button ever enables.

Two bugs reached a delivered zip on 2026-09-12 as a result: three unescaped
`innerHTML` sinks, and a block of markup inserted INSIDE billing.html's
`<script>` — which would have ended the outer script early and rendered the
rest of the page's JavaScript as visible text. Every static assertion about
that file still passed. It was found by reading, which is not a process.

### What exists now

`backend/test/browser/` — real Chromium, the real files from `frontend/`, a
stub API, and assertions about what a person would see.

`harness.ts` serves `frontend/` over HTTP, intercepts `/api/*` with a per-test
stub, seeds `sessionStorage` before any script runs (so a page that redirects
unauthenticated visitors can be tested at all), records every API call the page
made, and **fails a test on any uncaught page error** — which is the single
check that would have caught the stranded-markup bug outright.

The API is stubbed rather than run, deliberately. Route behaviour has its own
tests against real Postgres; what was untested is whether the PAGE calls them
correctly and does something sensible with the answer. Stubbing also makes a
500, an empty list or a hostile value trivial to arrange — which is where pages
actually break.

**18 tests today.** `byok.html`: the wording shown, the submit button staying
disabled until key + email + tick are ALL present, unticking re-disabling it, a
malformed email, the key posted once and then cleared from the DOM, a server
rejection leaving the form usable, dead links, no-token, the Anthropic variant,
the field being `type=password`. `billing.html`: no uncaught error on load, the
tab fetching and rendering a row per key, a non-active key saying plainly that
the firm is paying, only active keys offering "turn off", the disable posting
the right client, **a client name containing `<img onerror=...>` rendering as
text**, the empty state, invite creation, and a 500 surfacing rather than
blanking the panel.

### Proof it works, not an assertion that it does

Today's bug was put back — the pane moved inside `<script>` — and the suites
re-run:

```
  static tests   2 failed     (and both only exist because the bug was already
                               found by hand and a test written afterwards)
  browser tests  9 failed
```

### Docker

`deploy/test/Dockerfile` + `docker-compose.yml` + `deploy/run-ui-tests.sh`.

Base is `mcr.microsoft.com/playwright:v1.49.0-jammy`, **pinned**: `:latest`
would mean the browser under test changes without anyone deciding to change it
— the same class of problem as the voice harness recording on a different model
than production ran (v5.34.51).

Compose brings up Postgres alongside, so one command runs all three tiers:

```
bash deploy/run-ui-tests.sh          # unit + Postgres-backed + browser
bash deploy/run-ui-tests.sh browser  # just the browser suite
bash deploy/run-ui-tests.sh --native # no Docker; uses local Chromium
```

`deploy.sh uitest` is the same thing.

### The skip rule, which matters more than it looks

The browser suite runs inside `npx vitest run`, so `deploy.sh` on a Mac would
have tried to launch a Chromium that is not installed and failed every release.

So: **no browser → SKIP, loudly**, because a gate that cannot be satisfied
locally gets bypassed, and a bypassed gate is worse than none. **Inside the
container, `VYNE_REQUIRE_BROWSER=1` makes a skip a hard FAILURE**, because that
is the environment whose entire job is to have a browser, and a silent skip
there would mean the frontend quietly stopped being tested — the exact state
this work exists to end.

Both paths were verified by moving `/opt/pw-browsers` aside and re-running: 18
skipped with a warning, and a hard error under `VYNE_REQUIRE_BROWSER=1`.

### Unverified, and I will not pretend otherwise

**The Docker image has never been built.** This container has the docker CLI
but no daemon, so `run-ui-tests.sh`, the Dockerfile and the compose file are
syntax-checked and reasoned about, not executed. Everything they wrap — the
harness, the 18 tests, the skip logic, the resolver for both browser layouts —
IS verified, natively, here. The first `docker compose build` is the untested
step, and it is yours. If it fails it will fail at the image build, not in the
tests.

### The standing rule from here

Every round that touches a module ships regression coverage for that module,
and any page it touches gets a browser test. The customer is not the test suite.

## v5.34.57 — the audit was right, and the HIGH was mine

An external audit of v5.34.55 found two real defects. Both confirmed in the
code before anything was changed.

### HIGH — one secret per FIRM, not per client

`secretIdFor(tenantId)` took only a tenant and returned `vyne-byok-<tenant>`.
The DATABASE moved to client grain in migration 031; the SECRET STORE never
did. So every client's key in a firm was written as a successive VERSION of one
shared secret, and `getTenantKey` read `versions/latest`.

**The last client to supply a key would have become the key every client in
that firm resolved to.** Client A's interview transcripts processed through
Client B's Google account, and B billed for A — the exact cross-client leak
migration 031 was written to prevent, reintroduced one layer below where it was
fixed. Latent only because nothing resolves a stored key yet; it becomes real
the day the gateway resolver ships.

**And the test that "proved" separation was a lens.** `byokClientGrain.test.ts`
asserted `g.secretName !== a.secretName` — true only because its own `attach()`
helper fabricated `projects/p/secrets/vyne-byok-${provider}`, a shape the
production path never emitted. The test asserted a property of itself.

Fixed: `secretIdFor(tenantId, clientNorm, provider)`, and the persisted name now
carries a pinned **version** rather than resolving `latest` — which also makes a
stale cached key impossible rather than merely short-lived, since a rotation
produces a name that has never been cached. The grain test now calls the real
`putTenantKey` against a fake Secret Manager, so the name under test is the name
production writes.

### MEDIUM — an Anthropic key transmitted to Google

`redeem` called `probe(apiKey, {})` unconditionally, above the provider check,
and `probeKey` posts the value to `generativelanguage.googleapis.com` as
`x-goog-api-key`. Every Anthropic redemption therefore disclosed the client's
Anthropic key to Google, and then discarded the result.

Worse than the bug: the comment beneath it asserted "Anthropic keys are not
probed by the Gemini prober" — describing an intent the code did not implement.
A false comment stops the next reader from checking.

Fixed: the probe runs only for `gemini-aistudio`.

### LOW — the probe echoed to the invite holder

The 400 body returned the full `KeyProbe`, a bounded oracle over a key's
capabilities. Now returns the reason only.

### A third weakness, found while fixing the first

`secretIdFor`'s new guards were regex-only, and `/^[a-z0-9]+$/.test(undefined)`
coerces to the string `"undefined"` and PASSES. A caller that forgot the new
arguments would have produced a real, wrong, shared secret id instead of an
error. Found because a test expected a throw and did not get one. Type checks
now precede the shape checks.

### Negative controls for all three

| restore the defect | what fails |
|---|---|
| `secretIdFor` → tenant only | 5 tests |
| probe every provider | `an ANTHROPIC key is never sent to Google` |
| echo the probe in the 400 | `a rejection returns the reason, not the probe evidence` |

The MEDIUM control initially passed — the fix was in place with no test behind
it, which is how a defect returns. The test was written until the control
failed.

### What the audit could not see

It noted the gateway resolver was absent from the changeset. It still is:
nothing calls `activeKeyFor` or `getTenantKey` outside tests. The finding was
latent, and the fix lands before the consumer does.

## v5.34.58 — the skip guard did not cover the likelier absence

Reported from a real machine: `deploy.sh` failed on a fresh checkout with

```
Error: Failed to load url playwright-core ... Does the file exist?
 Test Files  2 failed | 91 passed | 19 skipped
```

v5.34.56 added a graceful skip for a missing BROWSER. The `playwright-core`
import was top-level, and a top-level import runs at module LOAD — before any
`describe.skipIf` can execute. So on a checkout that had not run `npm install`
since the devDependency was added, the suite failed to COLLECT and took the
release gate down with it.

The guard was written for the wrong absence. A missing browser is rare; a
missing node_module after a zip drop is the normal case.

**Fixed**: `playwright-core` is imported lazily inside the function that
launches it, types imported `type`-only (erased at compile time).
`browserAvailable()` now checks the package resolves before it looks for a
browser, and the skip message names WHICH prerequisite is missing —
`npm install` or a browser — so the fix is obvious from the output.

`run-ui-tests.sh --native` now installs the dependency rather than skipping,
because a native run is an explicit request for these tests.

**Verified by removing each prerequisite in turn:**

| removed | result |
|---|---|
| `node_modules/playwright-core` | 18 skipped, message names `npm install` |
| `/opt/pw-browsers` | 18 skipped, message names Chromium |
| either, with `VYNE_REQUIRE_BROWSER=1` | hard error naming which |
| neither | 20 passing |

And the whole default gate still passes with the package absent — 1,104, which
is the number that matters, because that is what `deploy.sh` runs.

**Negative control:** restore the eager import and
`nothing in this directory imports playwright at module load` fails.

### The lesson, which is not about Playwright

A skip guard is only as good as its list of prerequisites, and I listed the
interesting one instead of the likely one. The test now asserts the property
directly — no value import of playwright anywhere in that directory — rather
than trusting that the guard covers everything.
