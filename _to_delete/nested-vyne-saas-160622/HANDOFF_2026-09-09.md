# VYNE Platform — Handoff Notes (2026-09-09/10) — v5.34.22 → v5.34.30

Scope: the four live-voice symptoms from `FABLE_HANDOFF_live_voice.md` (S1 no reply,
S2 stuck mic button, S3 distortion, S4 fallback voice after refresh). Verified
behaviour in 5.34.21 (opening, pause/resume keepalive) was NOT touched.

## Diagnosis — what the code proves, and what it does not

**The "two systems fighting" hypothesis is real, but it is NOT what happens
before anyone clicks.** Traced every path that starts the legacy recogniser
(`VyneRecognition` in vyne-client.js — its own `getUserMedia` + `MediaRecorder`):
`toggleMic()` (the mic button), `onSpeakEnd()` (auto-mic after TTS), and the
resume branch of `setInterviewPaused()` when `LIVE` is null. On a clean live
interview none of these fire until a person clicks the mic. So the second
capture chain cannot explain the FIRST no-reply — it explains everything after
the interviewee gives up waiting and clicks.

| Symptom | Cause (proven from code unless marked) | Fixed by |
|---|---|---|
| **S2** stuck red "RECORDING" | The voice bar showed the standard controls on the live path — the placeholder literally said "Click 🎤 to start". `toggleMic()` then started `VyneRecognition`: a SECOND mic stream + MediaRecorder + the red banner, while the live session's own capture kept streaming. `VyneRecognition.start()` is async and silently no-ops if `_rec` exists, so a quick second click leaves it recording with nothing to stop it. | mic button is a no-op indicator while live owns the mic; recogniser is never built on the live path |
| **S4** "VYNE_Agent" after hard refresh | A refresh closes the socket but never ran `stop()`, so the server-side hold was never released. Holds count for 10 min against a cap of 3 (`routes/voice.ts`). The 3rd refresh in 10 min → `429 too_many_live_sessions` → the page's designed fallback: text model + TTS ("VYNE Agent" bubbles, default persona). Same mechanism as HANDOFF_2026-09-08 item 1. | `pagehide` → `LIVE.stop('page_unload')` → keepalive `/close` beacon (verified in headless Chromium: `/close` fires on reload) |
| **S3** distortion | Two mechanisms, both real: (a) after any moment where `liveActive()` was false (renewal in flight, grant lapsed), `sendToAgent` fell to the text path → `speak()` (TTS) → `onSpeakEnd` → auto-starts the recogniser. Now two voices AND two mics. (b) *Suspected, now instrumented*: the model interrupting itself on its own echo (`interrupted` with a quiet uplink) → `flush()` every few hundred ms = choppy audio. | (a) `speak()` is suppressed while live owns output; routing is by ownership not liveness; (b) `INTERRUPTED — barge-in {likelySelfEcho}` trace line |
| **S1** no reply after speaking | **Not provable from code — and no prior trace ever showed an `inputTranscription` frame for the interviewee.** "mic: N frames" only proved frames FLOWED. The candidates, in order: (1) the model never hears — uplink carries silence/garbage (browser-specific capture chain; Safari does not resample a mic stream into a 16 kHz context); (2) the model hears but VAD never closes the turn (continuous noise/echo keeps it "open"); (3) the model hears and answers, but only after a multi-second *thinking* phase — the UI showed "Listening..." throughout, which reads as dead and sends the person to the mic button (→ S2). | Instrumentation that separates (1)/(2)/(3) in one trace, the visible mic meter and per-turn status for (3), and an opt-in `thinkingBudget` knob for (3) |

The Gemini Live contract was re-checked against current docs: `realtimeInput.audio`
with `audio/pcm;rate=16000` and automatic VAD (default on) is exactly what
`buildAudioFrame` sends — no `activityStart/End` needed. Two facts worth knowing:
gemini-2.5 native audio has **dynamic thinking on by default** (the 3–15 s of text
frames before every reply, not just the opening; `thinkingBudget: 0` disables it),
and the WebSocket **connection** lifetime is ~10 min regardless of the 15-min grant
(handled by the existing renewal; now a typed message during the gap is held, not
sent to the text model).

## What changed (5.34.22)

**One owner.** `interview_agent.html`
- `liveOwnsConversation()` = `LIVE && !LIVE.stopped` — sticky through a renewal, ends
  only when live is over for good. `sendToAgent` routes on this, not on `liveActive()`.
- `toggleMic()`, `speak()`, `onSpeakEnd()` are no-ops while live owns the interview.
- The recogniser is built only on the standard path (on the tap, after live was not
  taken; or lazily in `toggleMic`). Never on a live interview.
- Live voice bar: 🎤 becomes an indicator with a **level meter** (green = the app hears
  you); placeholder says "just speak"; status shows "*Jack Smith* is thinking… /
  is speaking — you can interrupt / Listening...".
- `pagehide` releases the live grant.

**Bridge.** `vyne-live-interview.js`: `say()` holds text while no socket exists and
sends it into the renewed session; a failed renewal or a non-paused terminal end
sets `stopped=true` (live path over → standard path may take over cleanly).

**Instrumentation.** `vyne-live.js` (all in `vyneLiveLogDump()`):
- `mic: first frame sent {rms, peak, track{readyState,muted,label,rate,ec,ns,agc}}`
- `mic: SPEECH on uplink (utterance starts) {rms, msSinceTurnComplete, agentPlaying}` /
  `mic: utterance ends (~Ns of speech)`
- `!!! mic uplink SILENT for 8s while unmuted` → candidate (1) above. Badge shows it.
- `USER TURN #n — model transcribed the interviewee; awaiting its reply`
- `model ACTIVITY on user turn #n (Xms after transcript began)` / `reply FIRST AUDIO`
- `!!! NO MODEL ACTIVITY 12s after the interviewee was transcribed` → candidate (2).
  Badge shows it.
- `INTERRUPTED — barge-in {micRms, micInUtterance, likelySelfEcho}`
- `playback run starts {ctxRate, resampledByBrowser, leadMs}` / `run ends {chunks,
  audioSec, wallSec, stillQueuedSec}` / `!!! PLAYBACK OVERLAP` → S3 inside the queue
- `recognition.start()/stop() {liveOwns, via}`, `sendToAgent() {liveOwns, via}`,
  `callClaude() — TEXT path taking a turn {via}`, `speak() SUPPRESSED`
- DevTools: `await vyneLiveMicCheck(3)` → `{peakRms, speechLevel, track}` — say
  something after calling it.

**Opt-in.** `GEMINI_LIVE_THINKING_BUDGET=0` (Cloud Run env; forwarded by deploy.sh)
pins `generationConfig.thinkingConfig.thinkingBudget` into the token. Unset = wire
identical to 5.34.21. If Google rejects the field, the mint retries WITHOUT it and
stays pinned (the persona pin is never traded for the knob); the grant echoes
`thinkingBudget` so `grant minted` in the trace shows what applied. **Not verified
against the live API** — try it on staging first and read the `grant minted` line.

## By-ear verification (the only acceptable sign-off)

Fresh tab, hard reload (⌘⇧R), confirm the badge/version reads 5.34.22, DevTools open.

1. Tap to begin. Expect: `● Live voice — Sadaltager`; 🎤 shows a small bar under it;
   placeholder "Live voice — just speak…". Jack Smith speaks his opening (≤ ~7 s).
2. While he speaks: the bar should stay grey/low (your room). Interrupt him mid-
   sentence: he must stop within ~0.5 s. Trace: `INTERRUPTED — barge-in
   {micInUtterance:true, likelySelfEcho:false}`.
3. Answer a question (2–3 sentences), then stop talking. Watch three things in order:
   the bar goes green while you talk; status changes to "Jack Smith is thinking…"
   within ~2 s of you stopping; then "is speaking" and you hear the reply.
   Trace: `mic: SPEECH on uplink` → `USER TURN #1` → `model ACTIVITY on user turn #1`
   → `reply FIRST AUDIO … {msAfterUserTurn}` → `model turn ENDS`.
4. Click the 🎤 button. Expect a toast ("Live voice is on — just speak") and NOTHING
   else: no red RECORDING banner, no change of state. Trace: `CLICK: mic button while
   LIVE owns the mic — ignored`. There must be NO `recognition.start()` line anywhere.
5. Pause 15 s, Resume. Answer again → reply. Trace: `paused — sending silent
   keepalive` … `resumed — capture chain state {track.muted:false}` … `USER TURN #2`.
6. Type a sentence in "Type instead" and send. Reply must come in Jack's voice.
   Trace: `sendToAgent() {liveOwns:true}` and NO `callClaude()` line.
7. Hard-refresh three times in a row, tapping to resume each time. Every time must
   come back as `● Live voice`, never `○ Standard voice — too many open sessions`.
   Network tab: `POST /api/voice/live-session/close` on each refresh.
8. Let a session run past 10 minutes without pausing. Expect the badge to flash
   `reconnecting (1)` and Jack to continue; no VYNE Agent voice at any point.

If step 3 fails, the trace now says which of the three S1 candidates it is:
- `!!! mic uplink SILENT` → capture chain. Check `track.muted`, `label` (right device?),
  browser (Safari?), and run `await vyneLiveMicCheck(3)` while talking.
- `USER TURN #1` but then `!!! NO MODEL ACTIVITY` → server-side turn never closed.
  Look at what came BEFORE: `mic: SPEECH on uplink` lines that never get an
  `utterance ends` (constant noise/echo holding VAD open), or `INTERRUPTED
  {likelySelfEcho:true}` bursts. Headphones for one run isolates echo.
- `USER TURN #1` → `model ACTIVITY … kind:"thinking-text"` → `reply FIRST AUDIO` at
  8–15 s → it was latency all along. Set `GEMINI_LIVE_THINKING_BUDGET=0` on staging
  and re-run steps 1–3.

## 5.34.23 — what the first production trace of 5.34.22 showed, and what changed

Trace (Kishore, prod, 5.34.22), decoded against wall-clock since page load:

| t | line | meaning |
|---|---|---|
| 30.4 s | `model turn ENDS` | opening finished generating (playback ran on ~12 s) |
| ~43–50 s | 17.3 s "utterance" ends | opening echo + the interviewee's first answer (~7 s) |
| 50–101 s | **nothing from the server** | no `userTranscript`, no thinking text, no audio for 50 s |
| 59, 77, 84, 87 s | 0–0.9 s blips, rms 0.02 | "hello?" — quiet but speech-level |
| 92.7–97 s | 3.2 s utterance, peak 0.996 | a loud repeat |
| 101.4 s | `INTERRUPTED` + `turnHadAudio:false` | **the server WAS generating a turn that never produced a frame**, and the 101 s speech cut it |
| 111.1 s | audio run starts | reply, ~5 s after the 101–106 s utterance's VAD end — normal latency |
| 120.6 s | `INTERRUPTED` with `micRms:0.0002` | the server "heard speech" while our uplink was flat — it reacted to audio we sent **earlier** |
| 120.7 s | `mic uplink SILENT` | **false alarm** (noise-suppression floor); fixed below |

Reading: the uplink carried speech (levels 0.02–0.3, peaks to clipping), the capture
chain is fine, and the server did react — **late**. A turn open for 50+ s with no
output, then a reply, then an interruption from speech that ended 8 s earlier, is
the signature of a **delayed uplink**: the server hears every utterance seconds to
tens of seconds after it was said. Two places that delay can live: (a) in the
browser/network — `ws.bufferedAmount` climbing because the socket is not draining
(VPN, proxy, upstream bandwidth, server backpressure); (b) inside Google's pipeline
after it has our bytes. 5.34.22 could not tell them apart. 5.34.23 can.

### Changes
- **`wsBuffered` / `backlogSec`** on every mic rollup, utterance start/end and
  INTERRUPTED line; `!!! UPLINK BACKLOG — N s of audio is queued in the browser` once
  it passes 1 s; past 3 s frames are **shed** (`uplink SHEDDING frames`) so latency
  stays bounded instead of growing; `uplink backlog drained {droppedFrames}`.
- **No uplink before `setupComplete`.** Frames used to leave in the ~130 ms between
  our setup message and the server's ack. Google's client never does that.
  `setupComplete … {micFramesHeldBeforeSetup:N}` shows how many were held.
- **`!!! SERVER IGNORED ~Ns of speech-level uplink`** — a client-side utterance ≥1 s
  with no server reaction of any kind within 8 s, with a verdict: `uplink is QUIET
  (meanRms < 0.02)` or `level is fine — server-side turn detection`. Badge: "your
  voice is not reaching the interviewer". This is the line 5.34.22 could not write
  because it waited for a transcription that never came.
- **Silence detector** fixed: 15 s window, rms 0.0003 **or** peak 0.005 counts as
  non-silent, and an utterance resets it. Chrome's NS floor (0.0002–0.0008) no
  longer trips it.
- **Experiment flags** (persist across hard reload; default all OFF = wire identical):
  `vyneLiveFlags({micGain:3})` amplify uplink; `vyneLiveFlags({streamEnd:true})`
  send `audioStreamEnd` after each utterance (documented flush); `vyneLiveFlags
  ({manualVad:true})` disable server VAD and bracket utterances with
  `activityStart/activityEnd` from the client-side detector; `vyneLiveFlags(null)`
  clears. Active flags are logged as `EXPERIMENT FLAGS ACTIVE`.
- **Hear what the model hears:** `vyneLivePlayUplink(10)` plays the last 10 s of the
  exact PCM sent to Google; `vyneLiveDownloadUplink(30)` saves it as WAV.
- `INTERRUPTED` line now carries `msSinceLastUtteranceEnd`, `playbackPending`,
  `wsBuffered`, `uplinkQuietNow` (no more "likelySelfEcho" — it asserted a cause).

### Next run — what to look at, in order
1. Trace after the first answer: `wsBuffered` on the mic rollups. **Climbing into the
   tens of KB and `backlogSec ≥ 1` → the browser/network is the lag** (try another
   network / no VPN; the shedding keeps it usable meanwhile). **Flat near 0 → the lag
   is inside Google after it has the audio** → go to 2.
2. `SERVER IGNORED` lines: `uplink is QUIET` → `vyneLiveFlags({micGain:3})`, reload,
   repeat. `level is fine` → `vyneLiveFlags({streamEnd:true})`, reload, repeat; if
   still late, `vyneLiveFlags({manualVad:true})`.
3. If replies come but 10–20 s late with `thinking-text` in `model ACTIVITY … kind`,
   set `GEMINI_LIVE_THINKING_BUDGET=0` on the API service and redeploy.
4. `vyneLivePlayUplink(10)` right after an answer: you should hear yourself, clear,
   normal pitch. If not, send `vyneLiveDownloadUplink(30)`'s WAV with the trace.

## 5.34.24 — the 5.34.23 trace settles WHERE the fault is

Second production trace (Kishore, 5.34.23):
- `wsBuffered: 0, backlogSec: 0` on every line → **the uplink leaves the browser
  in real time.** Not the network, not the browser.
- 23.8 s answer, `meanRms 0.0586, peak 0.903` → **level is fine**, format verified
  (40 frames per 5.12 s = a true 16 kHz context).
- **Nothing** from the server for it, nor for a 2.7 s answer, nor three short ones.
  `!!! SERVER IGNORED ~23.8s … verdict: level is fine — server-side turn detection`.
- The 22 s opening produced **zero `outputTranscription` frames** although the
  client's setup asks for both transcriptions → the client's setup frame is not
  (fully) honoured on the constrained endpoint. This is the same class of silent
  behaviour as the v5.32.53 speechConfig incident: the endpoint ignores what it
  does not expect rather than rejecting it.
- Pause keepalive, resume, opening: all still correct.

Conclusion: **Google's side of the socket is not treating our realtime audio as a
user turn**, and the remaining causes are all about the server's turn/setup state,
not about capture. Each has a flag now.

### Changes
- **Token carries the extras.** The mint now pins `inputAudioTranscription`,
  `outputAudioTranscription` and (when the browser asks via `manualVad`) 
  `realtimeInputConfig.automaticActivityDetection.disabled` into the token, with
  the same shed-before-unpin ladder as the thinking budget. `grant minted` shows
  `pinnedExtras:{transcription, manualVad}`. **If transcripts start appearing
  only now, the client setup was being ignored — that alone is worth knowing.**
- New flags (persisted, default off): `legacyChunks` (audio as
  `realtimeInput.mediaChunks[]`, the older field — an ignored `audio` field would
  look exactly like this), `openingViaRealtime` (text as `realtimeInput.text`, so
  the session never mixes clientContent turns with realtime audio),
  `holdMicUntilFirstTurn` (no mic audio while the opening is generating/speaking).
  `manualVad` now also travels to the server.

### Run order (one flag per run, hard reload between, `copy(vyneLiveLogDump())` each)
0. **No flags.** Read `grant minted … pinnedExtras`. Speak one answer. If
   `agentTranscript`/`userTranscript` lines now appear and the reply comes → the
   client setup was the whole problem; done.
1. `vyneLiveFlags({holdMicUntilFirstTurn:true})` — tests "audio during the
   clientContent turn poisons the turn state".
2. `vyneLiveFlags({holdMicUntilFirstTurn:false, openingViaRealtime:true})` —
   tests "mixing the two input paths".
3. `vyneLiveFlags({openingViaRealtime:false, legacyChunks:true})` — tests "the
   `audio` field is ignored on this endpoint".
4. `vyneLiveFlags({legacyChunks:false, streamEnd:true})`, then
   `vyneLiveFlags({streamEnd:false, manualVad:true})` — server VAD end-of-turn.
5. `vyneLiveFlags(null)` to clear. Whichever run produces `USER TURN #1` → `model
   ACTIVITY` → `reply FIRST AUDIO` within ~5 s of you stopping is the fix; it
   then becomes the default in the next build and the other flags are deleted.

realtime audio as a turn and emitting transcriptions is the half that has never
worked — and v1alpha, second in the sweep, has never been tried on a real session.
That fits every trace better than any other single hypothesis.

- New flag: `vyneLiveFlags({v1alpha:true})` → sweep order starts with
  `v1alpha/BidiGenerateContentConstrained?access_token`. Trace shows `ws variant

## 5.34.27 — FOUND IT IN THE TRACE: Google rejects the audio turn (close 1007)

Fifth trace (5.34.25 frontend, still the OLD API — `pinnedExtras: undefined`, v1beta):

```
[VL + 24394ms] frame MODEL-TEXT  "**Analyzing the Utterance** I've processed the Hi… 'Have to achieve anything'…"
[VL + 26322ms] frame MODEL-TEXT  "**Formulating a Response** …"
[VL + 28402ms] ws CLOSE — code 1007 — The audio content type (CONTENT_TYPE_AUDIO) is not
               supported for this model configuration.
```
…and again 7 s later on the renewed session. Then a third session DID answer with
audio, then ignored a 24 s answer outright.

So the model **hears** the interviewee — its thinking quotes their words — and when it
goes to generate the reply, Google closes the socket: the model configuration does
not support audio content. Sometimes the reply survives, sometimes the socket dies,
sometimes nothing comes back at all; all three are the same server-side fault seen
from the client. The LiveKit community hit this exact close on 2026-09-06 on
`gemini-2.5-flash-native-audio-preview-12-2025`
(https://community.livekit.io/t/…/1737) — four days ago, same model family. Our
model is the `-latest` alias, which tracks whichever preview Google points it at.

Consequence that was invisible until now: each 1007 triggered an instant renewal =
a fresh grant. Two in 8 s. That is a second road to `too_many_live_sessions` and the
text+TTS fallback ("VYNE_Agent"), and every renewal starts a session with NO memory
of the conversation so far.

### Changes (client)
- `!!! GOOGLE REJECTED AN AUDIO TURN — 1007 CONTENT_TYPE_AUDIO` trace line with
  model/variant/pinned/thinkingBudget/pinnedExtras; badge "Google rejected your last
  answer (1007 audio) — reconnecting".
- Renewal after a 1007 waits 1.5 s; three consecutive 1007s end the live path with
  reason `audio_rejected` and a badge that says so, instead of burning the grant cap.

### What to change on the SERVER (this is where the fix is)
Deploy the API (it is still on a pre-5.34.24 build — `pinnedExtras: undefined`) and
set, in this order, one at a time:
1. **`GEMINI_LIVE_MODEL=models/gemini-2.5-flash-native-audio-preview-09-2025`** —
   pin off the `-latest` alias. If `-latest` now resolves to the 12-2025 preview that
   LiveKit users see failing, this alone may fix it. (This is not the "wrong model"
   mistake from 5.34.18 — both are on `LIVE_CAPABLE_MODELS`.)
2. **`GEMINI_LIVE_THINKING_BUDGET=0`** — the 1007 lands right after the thinking
   frames every time; thinking + audio input on a pinned config is the obvious
   interaction to remove.
3. v1alpha (default since 5.34.26) — the token endpoint is v1alpha; a v1beta session
   holding a v1alpha token is the other candidate for "this model configuration".

Sign-off is unchanged: opening → answer → reply within ~5 s, no `1007`, no `SERVER
IGNORED`, `agentTranscript` lines present, Pause/Resume, and a typed message answered
in Jack's voice.

## 5.34.28 — first v1alpha trace: it ANSWERS. Late. API still not deployed.

Seventh trace (5.34.26/27 frontend, v1alpha default; `!!! API BUILD MISMATCH` — the
API service is STILL on the pre-5.34.24 build):

| | v1beta (all earlier traces) | v1alpha (this trace) |
|---|---|---|
| opening: trigger → first audio | 7–10 s (thinking 5–7 s) | **4.3 s** (thinking 2.2 s) |
| reply to a spoken answer | never, or `1007 CONTENT_TYPE_AUDIO` | **yes** — twice, with audio |
| latency, answer end → reply | — | 13.5 s and ~28 s |
| `1007` closes | 2 in one run | **0** |
| transcription frames | none | none (extras not pinned — API not deployed) |

So the endpoint mattered: v1alpha talks back on this token; v1beta refuses or dies.
What is left is latency and one behaviour of the interviewee: after the first answer
the trace shows six 0.3–0.5 s utterances ("hello?") over 25 s, and `INTERRUPTED`
right after the first of them — each one cancels the reply the model was preparing
and starts it over. **After answering, stay silent until the reply starts.**

The 13–28 s is not the model thinking (thought summaries arrive ~0.5 s before the
audio); it is the server deciding the interviewee's turn has ended. That has
documented controls, now pinned into the token from env (API deploy required):

## 5.34.33 — long sessions, and a harness that does not need a human

The 3.1-flash-live run was good for ten minutes and then stopped, with a
probable sign-out. Three defects, all ours, all provable from code:

1. **A 401 or an idle expiry replaced the page mid-interview.** Both ends of
   the session policy in `vyne-client.js` finished with
   `location.href = "index.html?expired=1"`, whatever else was happening. The
   realtime socket talks to Google with an ephemeral token and needs nothing
   from our API, so the interview was still working when the page was taken
   away — and the in-memory trace went with it, which is why the failure could
   not be read afterwards. Now: the sign-out is deferred while a live session
   owns the page (`window.__vyneLiveActive`), the local token is dropped
   immediately either way, and the redirect fires when live goes idle or after
   a 20-minute cap.
2. **Idle was measured only from click/keydown/mousemove/touchstart.** A
   hands-free interview produces none of them, so the 30-minute sweep signed
   the interviewee out mid-sentence while they were audibly present.
   `vyne-live.js` now calls the exposed `vyneTouchSession()` on each utterance
   and each model turn: talking is activity.
3. **The trace died with the page.** It is now mirrored into localStorage
   (tail-bounded, flushed on pagehide) and the previous page instance's copy is
   readable with `copy(vyneLiveLogDumpPrev())`.

### 90–120 minute deep dives
- **`MAX_RENEWALS = 8` was a duration limit in disguise.** One handover per
  ~10 minutes means twelve for two hours; renewal nine ended the live path at
  about eighty minutes. Renewals are now bounded by DURATION
  (`VYNE_MAX_INTERVIEW_MS`, default 3 h) with a high count guard (40).
- **The concurrency guard refused the continuation of the session it had just
  admitted.** A handover mints a fresh grant; with any stranded holds in the
  rolling window (an earlier interview whose `/close` never landed — see
  defect 1) the renewal got a 429 and the interview stopped dead. The client
  now sends `renewalOf: <previous sessionId>` and `admitLiveSession` exempts a
  VERIFIED continuation from the concurrency check only — spend caps and the
  reservation are untouched, so the exemption cannot buy budget.
- **A stale `goAway` survived into the replacement connection** and handed it
  over again ~1 s later: two handovers where one was needed, an extra grant,
  and a second gap in the conversation. Found by the soak, not by a person.
  `_openSession` now clears `_goAwayPending` and the poll.
- **An interview that ends early is not lost.** `onEnded` saves
  synchronously (the turn-by-turn autosave is debounced 1.2 s, so the last
  exchange could be the one that never landed), says the answers are saved and
  names the resume code. `buildLiveContext()` feeds the recent transcript back
  in on resume via `priorTranscriptBlock()`, so the interviewer picks up
  instead of re-asking covered ground.

### Testing without a human (this was the ask)
- `backend/test/liveLongSessionSoak.test.ts` — drives the SHIPPED frontend
  modules through a full two-hour interview in ~6 seconds: 12 goAway
  handovers, 36 exchanges, the grants and closes they generate, against a fake
  Google that only issues resumption handles at turn boundaries. Asserts the
  interview never ends, every renewal carries the handle, holds do not
  accumulate, and the cap never refuses a continuation. Includes the negative
  control (without `renewalOf` the same handover IS refused) and a regression
  pinning the old 8-renewal death at ~80 minutes.
- `backend/test/liveSessionExpiryDeferral.test.ts` — runs the shipped
  `vyne-client.js` in a vm and asserts on NAVIGATION: a 401 mid-interview does
  not redirect, an idle expiry mid-interview does not redirect, both fire the
  moment live ends, an explicit sign-out is still immediate.
- `deploy/soak-live.mjs` — the unattended REAL-Google soak, which is the only
  thing that can answer "does Google still answer promptly at minute ninety".
  `GEMINI_API_KEY=… node deploy/soak-live.mjs --minutes 120 [--wav answers.wav]`
  streams audio in real time, rides the handovers with resumption handles, and

## 5.34.38 — the first clean measurements, and the confound in them

separate question of whether the 3.1 PREVIEW model is simply capacity-limited.

## 5.34.39 — FOUND IT: the project is being rate-limited by Google

Six unattended 10-minute runs, same afternoon, same script, same key.

| # | run | config | turns | answered | median | connection ends |
|---|---|---|---|---|---|---|
| 1 | base | default thinking, compress 25600 | 35 | 34 | **1,196 ms** | goAway, 1011 internal |
| 2 | think | thinkingLevel LOW | 28 | 28 | 2,719 ms | goAway, deadline |
| 3 | nocompress | compression OFF | — | — | (no verdict) | — |
| 4 | budget | thinkingBudget 0 | NEVER RAN | — | — | — |
| 5 | base2 | **identical to run 1** | 12 | 6 | **31,844 ms** | 1011 internal ×3, **1011 Resource has been exhausted (e.g. check quota)**, deadline |
| 6 | gen25 | 2.5 native audio | 8 | 3 | 4,961 ms | **1011 The service is currently unavailable** |

**Run 1 and run 5 are the same configuration.** 1,196 ms and 34/35 answered,
versus 31,844 ms and 6/12 answered. The only difference between them is how
much of the project's Live API allowance had already been spent, and run 5 says
so in Google's own words: *Resource has been exhausted (e.g. check quota)*.
Run 6 says the same thing differently: *The service is currently unavailable*.

So the answer to "why does the interview start well and then degrade" is not
the model, not the session length, not thinking, not context compression, not
the VAD settings, and not this code. It is a project-level rate limit, and
every one of those settings was tuned against its shadow. Three more things
that follow from the same evidence:

- **3.1 Live does not degrade with session length.** Run 1: flat ~1.2 s across
  34 turns and 10 minutes, one goAway handover ridden cleanly with resumption.
  The product is capable of a good long interview on a rested quota.
- **`thinkingLevel` is accepted by 3.1; `thinkingBudget` is still unverified**
  because run 4 never executed. That remains the one open configuration
  question, and it matters: the product pins `thinkingBudget`, so if 3.1
  rejects it the env var has been inert all along.
- **2.5 native audio exposes thought time** (`thought 2382ms of it`), which 3.1
  does not, and was also throttled — so this is not a 3.1-preview problem.

### Changes (product)
- `vyne-live.js` recognises a RESOURCE_EXHAUSTED close and names it:
  `!!! GOOGLE IS RATE-LIMITING THIS PROJECT`. It used to arrive as an ordinary
  close and present to the interviewee as silence, which is precisely why it
  survived nine releases of investigation.
- `vyne-live-interview.js` backs off instead of re-minting instantly — 15 s,
  30 s, 60 s, 120 s, then ends with the named reason `quota_exhausted`. The old
  behaviour reconnected within milliseconds, spending the allowance that had
  just run out; run 5's five connections in ten minutes are what that looks
  like. An ordinary 1011 still renews immediately.
- `interview_agent.html` tells the interviewee the truth — "Google is
  rate-limiting this project — your answers are saved; resume in a few
  minutes" — rather than leaving a silence they read as a broken product.
- Six tests in `liveTurnOwnership.test.ts` cover naming, the wait, the
  escalation, the named give-up, and that a plain 1011 is NOT treated as a
  rate limit.

### Changes (soak)
- "the model transcribed NOTHING — this is the fixture" is now only printed
  when nothing was transcribed in the WHOLE run. In run 6 the same clips were
  transcribed cleanly for three turns and then not at all, and the script
  blamed my harness for Google refusing to work.
- The verdict flags any quota/availability close and prints
  `INVALID FOR COMPARISON` rather than a latency table, because a throttled run
  measures the allowance, not the setting under test.

### What to do about the quota
Live API limits are per project and per usage tier, and audio burns tokens
fast (~25 tokens/second in each direction). Check the real numbers for this
project rather than guessing:

    https://console.cloud.google.com/apis/api/generativelanguage.googleapis.com/quotas?project=vyne-platform-prod

Look at the concurrent-session and tokens-per-minute limits for the Live
models, and request an increase if a 90–120 minute deep dive is the target: two
hours of audio at ~25 tokens/second each way is on the order of 360k tokens of
throughput for ONE interview, before any testing around it. Until then, space
soak runs and real interviews apart — back-to-back sessions are what produced
run 5.

### The one run still owed
    node deploy/soak-live.mjs --minutes 10 --thinking-budget 0 --out budget.txt
Run it from a rested quota. `setup accepted:` vs `REJECTED thinkingConfig`
answers whether the product's own thinking pin does anything on 3.1.

## 5.34.40 — the reply that arrives as TEXT and never as VOICE

I ran the soak myself this time, on the user's machine through the desktop
bridge (the cloud container and the device workspace are both blocked from
`generativelanguage.googleapis.com` by the org egress policy — an allowlist
entry was added, but policy is bound at session start, so it takes a new
session to apply).

Fresh baseline, ~30 minutes after the previous day's runs: 16 turns, 13
answered, median 3,693 ms, p90 28,282 ms, quarters **17,542 → 9,214 → 3,141 →
2,638 ms**. It got FASTER through the run. Connection 1 was erratic (896 ms,
28.3 s, 23.4 s, 20.8 s, …) and died on `1011 Internal error`; the RESUMED
connection 2 then ran six turns at 1.6–4.1 s. So there is no monotonic
degradation to chase — there is variance, and at the extreme, the quota wall
found in 5.34.39.

**But turn 5 is the find:**

    conn 1 turn 5: reply NONE
      | heard "Skills are the part I worry about most. We can hire data eng"
      | said  "How is the organization addressing that knowledge gap on the business side?"

A healthy socket. The model UNDERSTOOD the answer and COMPOSED its next
question — the output transcript is right there — and sent no audio at all.
`liveAppend` renders that transcript into the chat, so the interviewee is
left reading a question nobody asked aloud, in an unexplained silence. That
is the "VYNE Agent was typing text… there were very long gaps" report from the
very first day, and no amount of latency, VAD or thinking tuning could ever
have addressed it, because the reply was not late: it was MUTE.

### Changes
- `vyne-live.js` accumulates the turn's output transcript and, after
  `VYNE_MUTE_REPLY_MS` (6 s default) of text-without-audio, logs
  `!!! REPLY WITH NO VOICE` and calls `onReplyWithoutAudio(text)`. A
  `turnComplete` carrying a transcript and no audio fires it immediately —
  there is nothing left to wait for. Audio arriving cancels the timer, and if
  the app had already started speaking, `onAudioArrivedLate` tells it to stop.
- `interview_agent.html` speaks that text with TTS. This is the ONE exception
  to "TTS never plays over a live session" (S3 in the original handoff), and it
  is bounded: only the turn's own text, only when no audio came, cancelled the
  instant Google's voice arrives, and never while paused. The badge says "no
  voice from Google on that reply — reading it aloud". This is also why the TTS
  model fix in 5.34.37 mattered: the fallback would have 404'd.
- Six tests: the mute window, no fallback when audio is timely, cancel on late
  audio, immediate fire on turnComplete, silence while muted.

## 5.34.41 — the 5.34.40 fallback made the voice choke; it is now opt-in

First real interview on 5.34.40: "the voice is choking every other second —
stop-go-stop-go". That is a regression I introduced, and the mechanism is in
this file's own history.

`vyne-live.js`'s INTERRUPTED handler resets `_turnAudio = false` on a barge-in
(correctly — the turn's audio was flushed). 5.34.40 read that flag as "no voice
has come for this turn", so the six-second mute-reply timer re-armed MID-TURN,
the TTS fallback started speaking, the microphone picked up that speech, Google
read it as another barge-in and flushed its playback again. Stop, go, stop, go.
The comment directly above the reset already names this shape as the
self-cancelling agent that reads as "distortion" (S3) — the exact failure this
project opened with.

The judgement: a mitigation for an occasional text-only reply must never
degrade the voice path it exists to protect. So the halves are separated —
- **Detection stays ON, always.** `!!! REPLY WITH NO VOICE` and `!!! MUTE TURN`
  still appear in the trace, because naming that failure cost two soak runs to
  discover and costs nothing to keep.
- **Speaking is OFF by default**, behind `vyneLiveFlags({ speakMuteReplies: true })`.
- **And when enabled it is guarded**: never while playback is pending, never
  after this turn was interrupted (`_turnWasInterrupted`, cleared at
  turnComplete), never while muted.

Five tests pin it, including the regression itself: speak + interrupt +
transcript must produce no fallback voice.

### Also: the interviewer has a name
Every chat bubble said "VYNE Agent" from a hardcoded string, while the assigned
identity (`S.interviewerName`, e.g. "Jack Smith") is what the persona
introduces itself as and what the voice says aloud in its first sentence — two
different people in one conversation. `agentLabel()` and `agentInitials()` now
resolve the live session's interviewer name, falling back to "VYNE Agent" only
when no identity was assigned.

## 5.34.42 — the 10-minute handover was a coin flip, and a lost toss killed the interview

The interview on 5.34.41 ran well for ten minutes and then went permanently
silent. The trace says exactly why, with no inference needed:

```
587703  setupComplete — session is live
587705  sendText -> WIRE  "Our connection was briefly renewed…"
598390  userTranscript "Are you there?"
610394  !!! NO MODEL ACTIVITY 12s after the interviewee was transcribed
```

**Two milliseconds after setupComplete.** That is precisely the warmup instant
`open()` exists for — this file has said since 5.34.16 that "setupComplete does
not mean the model can generate yet; a turn sent in that instant is sometimes
silently dropped", and 5.34.17/.19 built resilient retry machinery around it.
All of it protected the OPENING only. The renewal nudge, sent on every ~10-minute
goAway handover, went out as a bare `say()` — no liveness check, no retry, no
alarm. So every handover was a coin flip, and a lost one left the interviewee
talking to a socket that would never answer, for the rest of the interview.

Two changes, both in `frontend/vyne-live-interview.js`:

1. **The nudge goes through `open()`.** Same code, same guarantee as the
   opening: reset the new session's frame flags, send, and resend ONCE if
   nothing at all comes back (`VYNE_OPEN_RETRY_MS`, 12 s). A model that is
   merely *thinking* has set `_gotAnyModelFrame` and is left alone — the
   5.34.19 lesson about four resends restarting the introduction applies here
   unchanged.

2. **`_watchRenewedSilence()` — a resumed session that is itself wedged.**
   `open()`'s retry rescues a dropped turn; it cannot rescue a connection that
   is alive and mute, which is what the trace above actually shows (empty
   `speechState` frames for the rest of the interview). If no model frame of any
   kind arrives within `VYNE_RENEW_SILENCE_MS` (20 s) of a handover, the
   resumption handle is **dropped** and a fresh connection is minted. A handle
   that yields a mute session is worse than no handle, because the alternative
   is not amnesia: `buildLiveContext()` still carries the recent transcript
   across, so the interviewer picks the thread back up without Google's own
   memory of it. One recovery attempt per renewal; if the fresh connection is
   mute too, the interview ends with the named reason `renew_silent` — which
   goes through the 5.34.33 synchronous save, so the answers survive and the
   session code resumes.

`isRenewable()` gained `renew_silent_retry`. `_openSession()` clears the
watchdog alongside the stale goAway. The page shows "Reconnecting your
interviewer" on `onRenewSilent` and a resume message on `renew_silent`, rather
than leaving the interviewee listening to nothing.

Six tests in `liveTurnOwnership.test.ts`, all against the shipped frontend in a
vm: the nudge lands on the NEW socket and is resent into total silence; it is
NOT resent when the model is thinking; a mute resumed session drops the handle
and reconnects (asserted on the grant body — `resumeHandle` present on the
renewal, absent on the recovery); a second silence ends with `renew_silent`; and
a renewed session that DOES speak is never torn down.

### Not a code change: what "Clarify this answer" is
It appears under the **interviewee's own** answers
(`!isAI && !extra.docInfo && !extra.isClarification`), never under Jack's
questions. It opens a box to amend or expand what they just said — the wording
is being read as "the agent could not understand you", which is why it showed up
in the same breath as the silence. Worth renaming to something like
"Add to this answer".
